UFS on MT6991: the bug, the fix, and the G5 puzzle

Why gear and lane changes failed, why one line fixed them, and what we've learned since about G5 speed. Explained from scratch.

Written 1 November 2026 · MediaTek MT6991 SoC evaluation board (k6991v1_64) · Android GKI kernel 6.6 (android15-6.6) with MediaTek vendor modules · Stands on its own: the earlier write-up isn't needed
The whole story on one page
  1. The board's kernel has a debugfs file, power_mode. Writing six digits to it (for example 552211) sets the gear, lanes and mode of the link between the processor and its UFS storage chip.
  2. It failed whenever the board had been quiet for more than about half a second: first with a PMC timeout, then with exit h8 state fail.
  3. The cause: the first line woke the UFS controller but not the chip side, which Linux represents as the W-LUN. Since Linux 5.14 those two wake separately. After half a second of quiet the chip is in Sleep and the link is in software hibern8, and only the W-LUN's wake-up undoes that.
  4. The fix was one call: ufs_debugfs_get_user_access(), which runs ufshcd_rpm_get_sync() and wakes the W-LUN (and the controller first). On the board: no more failures, lane changes work, and fio speeds follow the gear.
  5. Then a new question: G4 and G1 give steady numbers, but G5 writes to /data wander between about 3000 and 3700 MB/s.
  6. Why only G5: every write passes through the CPU, an encryption engine, the controller, the link and the chip, and the slowest of them sets the speed. Up to G4 the link is the slowest by far. At G5 it no longer is, so one of the others shows through.
  7. The new finding: the controller's AES encryption engine has its own clock, 416 or 546 MHz, and only MediaTek's own helper ever changes it. Gear changes through power_mode don't. During the steady-3000 run it sat at 416 MHz.
  8. Also measured: the controller's main clock drops to 273 MHz only while the disk sleeps at G5 (MediaTek's sleep and wake hooks), and SQPOLL in fio raised a 4 GB run from 3200 to 3800 MB/s, so the CPU can be a limit too.
  9. Not yet proven: that the slow encryption clock is what holds G5 writes near 3000. One clean run settles it (4.11).
  10. Recommended now: drop the ported clock-scaling block (file 07), and set MediaTek's clocks fast and locked once per boot (echo 5, then echo 4, to clkscale_control).

1The bug

1.1 What was being built

The goal: change the UFS link's gear and lane count at runtime on the MT6991 evaluation board, so the storage can be tested at each speed.

MediaTek's driver already offers a control file, clkscale_control (section 4.3), but it only knows two settings, "fast" and "slow". The goal needed any gear and any lane count, so a debugfs file, power_mode, was added to the UFS core's drivers/ufs/core/ufs-debugfs.c. The code was ported from the Qualcomm SoC kernel, msm-4.19 (ufsdbg_config_pwr_mode(), file 04 in this folder).

You write six digits, GGLLMM: gear RX, gear TX, lanes RX, lanes TX, mode RX, mode TX. Mode 1 is FAST (the high-speed HS gears) and 2 is SLOW (the slow PWM gears). So:

You writeMeaning
552211HS-G5, two lanes each way, FAST mode
442211HS-G4, two lanes, FAST
551111HS-G5, one lane each way, FAST
112211HS-G1, two lanes, FAST

The mode digits have two more values: 4 is FASTAUTO and 5 is SLOWAUTO, the same speeds except that the link may drop into a lower-power state on its own between bursts of data. MediaTek's negotiation doesn't accept them, so the ported function maps them to FAST and SLOW (2.3).

Two meanings

"Two lanes" means two per direction: 2 TX and 2 RX, four wire pairs. In the six digits, the lane part 22 is one digit for RX and one for TX.

"Power mode" has three meanings in this story, and the bug involved all three at once:

  1. Link power mode (UniPro): FAST, SLOW, FASTAUTO, SLOWAUTO, the link's speed setting. The digits set this.
  2. Chip power mode: Active, Sleep, PowerDown, set by sending the chip the SCSI command START STOP UNIT (SSU).
  3. Linux runtime PM state of a struct device: active or suspended (3.2).

The write runs ufsdbg_power_mode_write(), which parses the digits, keeps the current rate (A or B), checks the request with ufsdbg_power_mode_validate(), compares it with the chip's maximum in ufsdbg_cfg_pwr_param(), and then calls ufsdbg_config_pwr_mode(), which carries out the power mode change (PMC).

The ported function, step by step

As of 31 October, the ported ufsdbg_config_pwr_mode() does this:

  1. Gets access to the hardware. Originally with pm_runtime_get_sync(hba->dev); now with ufs_debugfs_get_user_access(hba) (2.2).
  2. ufshcd_hold() keeps the controller's clocks on. Apart from runtime PM, the core also switches the controller's clocks off during short idle gaps. This is called clock gating, and on MediaTek it kicks in after at least 10 ms. "Hold" blocks it while the code works.
  3. down_write(&hba->clk_scaling_lock) keeps the core's clock scaling and its internal management commands (queries to the chip) from running at the same time. It's 6.6's replacement for msm-4.19's hba->lock. The error handler is held off by host_sem, which user access takes (2.2).
  4. ufshcd_scsi_block_requests() tells the SCSI layer to stop sending new reads and writes.
  5. ufshcd_wait_for_doorbell_clr() waits until every command already sent has finished, that is, until the doorbell register (0x58) reads all zeros.
  6. The ported clock lines (4.10) and ufshcd_config_pwr_mode(), which runs MediaTek's PRE_CHANGE hook, then the PMC, then the POST_CHANGE hook (1.4).
  7. Undoes everything in reverse order.

Where the ported code lives: core and vendor

On Android, one generic kernel image is built for every phone, the GKI (Generic Kernel Image). The UFS core is part of it: drivers/ufs/core/ufshcd.c, ufs-debugfs.c and their friends. MediaTek's UFS code (ufs-mediatek.c, ufs-mediatek-sysfs.c, …) is a vendor module loaded on top, from kernel_device_modules.

The core calls into the vendor module through vops ("variant operations"): a table of function pointers that MediaTek fills in. The ones in this story are:

  • pwr_change_notify, called just before a PMC (PRE_CHANGE) and just after it (POST_CHANGE);
  • suspend and resume, called when the chip side goes to sleep or wakes (3.3);
  • setup_clocks, called whenever the core turns the controller's clocks on or off;
  • clk_scale_notify, called around the core's clock scaling, which is off on the board (4.3).

The debugfs file lives in the core. It can call core functions, but it can't see MediaTek's private data (struct ufs_mtk_host) or call MediaTek's private functions. That's why the fix had to use a core helper, why the core can't move the encryption clock (4.4), and why a change to this file needs a new kernel image, not just a new vendor module.

Two meanings: debugfs and sysfs

Both are files the kernel invents on the fly. sysfs (/sys) is the stable interface for real users; MediaTek's clkscale_control lives there. debugfs (/sys/kernel/debug) is for developers and can change at any time; the power_mode file lives there.

1.2 The two errors, and when they appeared

Seen on the boardYou hit two different messages, one per version of the ported function:

  • First version, which called ufshcd_change_power_mode() directly, the way Qualcomm's code does: pwr ctrl cmd 0x… with mode 0x… completion timeout, after half a second. It was first reported as "pmc command timed out".
  • Second version, which went through ufshcd_config_pwr_mode() so that MediaTek's hooks run: exit h8 state fail, followed by a full reset of the controller.

Both appeared only when the board had been quiet for more than about half a second. When you type commands into a shell, that's almost always. If something had just used the disk, the write could succeed, which is what made the bug so confusing. Part 3 explains why the half second matters.

1.3 The hardware, from scratch

Two chips and some wires. The UFS controller is a block inside the MT6991 processor (the SoC). The UFS chip is a separate package on the board: its own small controller plus the flash memory. Between them run the lanes: each lane is a pair of wires carrying data in one direction, so "two lanes" means two pairs each way, four pairs in all. The electrical standard for those wires is MIPI M-PHY.

The CPU never touches the wires. It reads and writes the controller's registers: memory addresses wired to hardware instead of RAM. Writing a number there makes the hardware do something; reading one tells you what it is doing. The controller's registers start at 0x16810000 (mt6991.dts:6686). Four of them matter in this story:

OffsetNameWhat it does
0x18AHIT (auto-hibernate idle timer)How long the link may sit idle before the controller puts it to sleep by itself. 0 turns the timer off (3.1).
0x58Transfer request doorbellOne bit per command slot. The driver sets a bit to start a command; the controller clears it when the command is done.
0x90UIC commandCommands for the link itself: wake it, put it to sleep, read or change a link setting.
0x14CMediaTek link state (REG_UFS_UFS_MMIO_OTSD_CTRL)MediaTek-specific. Its top byte says whether the link is up, down or asleep (3.1).

Three layers of rules on the wires

UFS transport (UTP)Carries SCSI commands (READ, WRITE, START STOP UNIT) in packets called UPIUs. This is what the files are made of.
UniProThe link layer: packs bits into frames, numbers them, confirms delivery, resends lost ones, and negotiates speed and sleep with the other end. Its lowest part is the PHY Adapter (PA); settings named PA_… live there.
M-PHYThe electrical layer: drives the voltages, recovers bits and timing at the other end, puts the wires to sleep and wakes them.

The chip runs the same three layers on its side. Every one of them has to agree before data moves.

Plain words

UFS transport is the letter. UniPro is the post office: it numbers the letters, confirms delivery and re-sends lost ones. M-PHY is the road.

Gears: how fast the wires flip

A gear is how many bits per second each lane carries. The high-speed gears run from G1 to G5, and each doubles the one before. MediaTek uses "rate B", one of two slightly different base frequencies.

GearBits per second per laneOne bit lastsCeiling, 2 lanes, before overhead
HS-G11,457.6 million686 ps~290 MB/s
HS-G22,915.2 million343 ps~580 MB/s
HS-G35,830.4 million172 ps~1.17 GB/s
HS-G411,660.8 million86 ps~2.3 GB/s
HS-G523,321.6 million43 ps~5.7 GB/s

G1 to G4 send every 8 bits of data as 10 bits on the wire (8b/10b), which keeps the signal balanced and lets the receiver stay locked to the timing. That's why the G1 to G4 ceilings are bit rate × 0.8 × lanes ÷ 8. G5 uses a more efficient code, so its ceiling is closer to the raw rate. Real throughput always lands below the ceiling because of protocol overhead. There is also a slow family, the PWM gears, used for bring-up and low power.

To make G5 physical: one bit lasts 43 picoseconds. In that time a signal on a circuit-board trace travels about 6 or 7 millimetres. That is why G5 leaves very little margin on an evaluation board with connectors and long traces, and why G4 and G5 need the link to train itself (equalization, called ADAPT in UniPro) each time it enters those gears.

The clocks and supplies that matter later

From the codeInside the controller, two clocks matter for speed. Both are multiplexers ("muxes") that pick one of two sources (mt6991.dts:6700 to 6753):

ClockWhat it drivesSlow sourceFast source
ufs_sel (named ck_sel on the board)The controller itself: how fast it moves data between memory and the link273 MHz, ck_mainpll_d4_d2499.2 MHz, ck_univpll_d5
ufs_fde (named ck_aes_ufsfde_sel)The inline AES encryption engine (4.5)416 MHz, ck_univpll_d6546 MHz, ck_mainpll_d4

The fast ufs_sel source needs the SoC's core voltage, vcore, held at 0.65 V or more (clk-scale-up-vcore-min = <650000>, mt6991.dts:6751). The link itself has separate clocks that follow the gear: unipro_tx_sym, and one receive clock per lane, unipro_rx_sym0 and unipro_rx_sym1 (mt6991.dts:6723), because each lane's receiver recovers its timing from the bits arriving on it.

The chip runs on two supply rails, made by a separate power-management chip, the PMIC (an MT6363 here). Only the host switches them; the chip has no say:

  • VCC feeds the flash memory (vcc-supply = <&mt6363_vemc>, mt6991.dts:6752).
  • VCCQ, 1.2 V, feeds the chip's own controller and its end of the link (vccq-supply = <&mt6363_vufs12>, mt6991.dts:6753).
Two meanings

"Host" can mean the controller hardware, Linux's SCSI host object, or loosely the whole phone. "Device" can mean the UFS chip or any struct device in Linux's tree of objects. In this document, the controller and the chip always mean the hardware, and a plain "device" means a Linux object.

1.4 A power mode change, call by call

Changing gear, lanes or mode is a power mode change (PMC). Both ends of the link must switch at the same moment, so a PMC is a conversation:

  1. The driver writes the new settings into the controller's UniPro attributes: PA_RXGEAR, PA_TXGEAR, the active lane counts, termination, the HS series (rate A or B), and some timeout values.
  2. It writes PA_PWRMODE. That write is the "go".
  3. UniPro sends a power-change request across the wires and waits for the chip's confirmation. UniPro calls these control frames PACP_PWR_req and PACP_PWR_cnf.
  4. When the exchange finishes, whether it worked or not, the controller raises an interrupt with the result. "Local success" means done.

It can fail in three ways, and each prints something different:

After any of them, unless a suspend or resume is in progress, the core marks the link broken and schedules the error handler (ufshcd.c:4270 to 4272). The error handler resets the controller and brings the link back up at its maximum gear, so the requested gear is lost.

Two more details from the same code. If you ask for exactly the mode the link already has, the core sends nothing and returns success (ufshcd.c:4566). And the core prints nothing when a PMC succeeds (ufshcd_print_pwr_info() uses dev_dbg, ufshcd.c:697). The PMC Success! lines you may see in dmesg come from MediaTek's own clkscale_control path, not from power_mode.

Key point

A PMC is a conversation over the link. If the link is asleep, nobody answers.

2How it was found, and what changed

2.1 The investigation, in order

  1. The setup. MediaTek's driver offered only clkscale_control, so the debugfs power_mode from the Qualcomm SoC kernel was ported into the GKI core.
  2. Error 1, the PMC timeout. The first version sent the PMC straight through ufshcd_change_power_mode(). After half a second without an answer, the core gave up (1.4).
  3. Error 2, "exit h8 state fail". Routing the call through ufshcd_config_pwr_mode() made MediaTek's PRE_CHANGE hook run first. It tried to make sure the link was awake, waited 100 ms, and complained (ufs_mtk_auto_hibern8_disable(), ufs-mediatek.c:2997).
  4. Reading three code bases side by side. Qualcomm's msm-4.19 debugfs code, where the first line came from. The 6.6 UFS core, where runtime power management lives today. MediaTek's vendor module, where the hook that complained lives.
  5. The key observation. The first line, pm_runtime_get_sync(hba->dev), wakes only the controller. Since Linux 5.14 the chip side, the W-LUN, has its own sleep and wake, and only its wake takes the link out of software hibern8 (Part 3).
  6. The fix, 31 October. One call replaced: no more failures, and lane changes from 2 to 1 pass.
  7. 1 November. A review of the whole function, a clean version (file 07), and the G5 investigation that fills Part 4.

The path in more detail

  1. The question. The starting point: the board, clkscale_control, the ported debugfs code and the two errors, and a search for a ready-made fix.
  2. The search. We went through upstream Linux, MediaTek's vendor trees and the patch archives. No patch fixes this exact failure. Two are related, and neither fixes it: 7dec5cedf7b2 ("scsi: ufs: core: Serialize AHIT register access between sysfs and host driver") and f29ec85ac4fd ("scsi: ufs: host: mediatek: Return error directly on idle wait timeout"). We downloaded MediaTek's MT6991 vendor code (a public copy), the android15-6.6 core files and Qualcomm's msm-4.19 ufs-debugfs.c, so the three could be read side by side. They are now in sources/.
  3. One step at a time. The first explanation was too compressed, so we slowed down and went through it a question at a time: what disabling auto-hibern8 actually does, whether the link must be up before a PMC, why the W-LUN's suspend would have sent DME_HIBERNATE_ENTER, and why there's a separate step that powers UniPro down.
  4. Code to compare. Files 01 to 05 were written into this folder, to open side by side in an editor.
  5. The flow. The ported code's sequence: pm_runtime_get_sync(), hold, lock, block, doorbell, PMC, plus the ported clock lines. Its first step was the root cause: it woke hba->dev, not the W-LUN.
  6. The clock question. Keep the ported clock-scaling lines, or copy MediaTek's? On 31 October we settled on keeping them, setting clkscale_control to 4 first, and never mixing with 1 or 3. On 1 November that changed: delete them (4.10).
  7. The ported code. The code switched to ufs_debugfs_get_user_access() (from file 05) on 31 October. It was copied into file 06, with two more fixes marked.
  8. The test. We rebuilt the kernel image, set clkscale_control to 4 and wrote power_mode: no exit h8 state fail. Then the lane tests passed too. The echo 4 turned out not to be needed for the fix (4.3).

Before (as ported from Qualcomm msm-4.19)

        return ret;

...

From the codeThe new call is the UFS core's own helper, the one its other debugfs files already use (ufs-debugfs.c:68):

static int ufs_debugfs_get_user_access(struct ufs_hba *hba)
__acquires(&hba->host_sem)
{
        down(&hba->host_sem);                    // one big UFS job at a time
        if (!ufshcd_is_user_access_allowed(hba)) { // refuses during shutdown
                up(&hba->host_sem);
                return -EBUSY;
        }
        ufshcd_rpm_get_sync(hba);                 // wake the W-LUN
        return 0;
}

And ufshcd_rpm_get_sync() is a one-line wrapper (ufshcd-priv.h:344):

static inline int ufshcd_rpm_get_sync(struct ufs_hba *hba)
{
        return pm_runtime_get_sync(&hba->ufs_device_wlun->sdev_gendev);
}

It's the same pm_runtime_get_sync() as before. The only difference is which device it names: the W-LUN instead of hba->dev. Which device you name decides what wakes up. What now happens when you write power_mode after half a second of quiet:

  1. The controller wakes first (Linux wakes a device's parents before the device): power domain, supplies, clocks, interrupt.
  2. The W-LUN wakes: DME_HIBERNATE_EXIT (link UP), START STOP UNIT (chip Active), AHIT timer back on.
  3. MediaTek's PRE_CHANGE hook turns AHIT off and checks 0x14C. The link is already UP, so the check passes at once.
  4. The PMC runs over an awake link. POST_CHANGE puts AHIT back.
  5. The code releases everything, and half a second later the chip side sleeps again.

2.3 The other changes in the ported function

The mode digits: map AUTO, don't force FAST

        if (desired_pwr_mode->pwr_rx == FASTAUTO_MODE)
                desired_pwr_mode->pwr_rx = FAST_MODE;
        else if (desired_pwr_mode->pwr_rx == SLOWAUTO_MODE)
                desired_pwr_mode->pwr_rx = SLOW_MODE;
        desired_pwr_mode->pwr_tx = desired_pwr_mode->pwr_rx;

From the codeMediaTek's ufs_mtk_pre_pwr_change() (ufs-mediatek.c:1908) sets up a high-speed host by default and switches to PWM only if SLOW was requested. It then calls the shared negotiation helper ufshcd_get_pwr_dev_param() (in ufshcd-pltfrm.c, not copied here), which treats only FAST as "high speed". A FASTAUTO request therefore fails negotiation. MediaTek prints "failed to determine capabilities" and carries on with empty settings. Mapping the AUTO modes avoids that, and keeps SLOW requests as PWM. An early version of this block forced FAST for everything, which would have turned every PWM request into HS; that was wrong.

Don't report success after a queued reset

        if (!ret && hba->ufshcd_state != UFSHCD_STATE_OPERATIONAL)
                ret = -EIO;

MediaTek's hook can fail, queue a reset and still let the PMC report success. This turns that case into an error. The states (ufshcd.h:529):

ValueStateMeaning here
0UFSHCD_STATE_RESETBeing reset
1UFSHCD_STATE_OPERATIONALAll good
2UFSHCD_STATE_EH_SCHEDULED_NON_FATALError handler queued for a minor error
3UFSHCD_STATE_EH_SCHEDULED_FATALReset queued. This is what MediaTek's failed check sets.
4UFSHCD_STATE_ERRORRecovery failed

The validate function

Qualcomm's original ufsdbg_power_mode_validate() accepts gears up to G4 and only FAST or FASTAUTO, so it rejects G5 and every SLOW request. The version in file 06 accepts G1 to G5 and all four modes. ufsdbg_cfg_pwr_param() still refuses anything above the device's maximum gear or lane count, with the message "exceeds device limitation".

2.4 Is the whole function OK? A review

Yes: the part that matters is right, and not by luck.

  • It does the same steps, in the same order, as the core does before its own gear changes (ufshcd_clock_scaling_prepare(), ufshcd.c:1319): wake, keep the clocks on, take clk_scaling_lock, stop new commands, wait for the ones in flight, then the PMC.
  • The wake is the core's own helper.
  • The PMC goes through ufshcd_config_pwr_mode(), so MediaTek's hooks run. Those hooks send only link commands (DME), nothing that needs clk_scaling_lock, so holding that lock for writing can't deadlock against them.

Three things still worth changing:

  1. Delete the ported clock-scaling block. On the board it moves one clock in a way MediaTek's own code never does, and it can't touch the clock that matters for encrypted writes (4.10).
  2. Move the debug dumps. If ufshcd_dump_uic_state() reads controller registers (its body wasn't available), two of its calls can run with the clocks off: the "before hold" one, and the one in the access-failure path. MediaTek turns the clocks off 10 ms after the last command (clk_gating.delay_ms = max(ah_ms, 10U), ufs-mediatek.c:1471), but the W-LUN stays awake for about 500 ms. In that gap the wake does nothing and the clocks are off, and a register read there can hang the bus. Move the first call below ufshcd_hold(), and delete the failure-path one, which only runs during shutdown.
  3. Set MediaTek's clocks fast and locked once per boot (echo 5, then echo 4; 4.3 and 4.12).
Watch out

Any UFS error resets the link to maximum gear and lanes, without telling you. After each benchmark run, check dmesg | grep "err_handler started". If that line appears, the run wasn't at the requested gear.

2.6 The #if 0 manual hibern8 exit

The ported code has a disabled block that called ufshcd_uic_hibern8_exit() directly. It aimed at the right symptom, but it would only have woken the link:

  • The chip would still be in Sleep from START STOP UNIT.
  • The core's records would still say the W-LUN is suspended and the link is in hibern8, because ufshcd_uic_hibern8_exit() doesn't update hba->uic_link_state; its callers do (ufshcd.c:4413).

Waking the W-LUN does all three things, in the order the core expects.

3Why it happened

3.1 Hibern8: the link's sleep, and who wakes it

What hibern8 is, physically. It is the deepest power state of the lanes that still keeps the link's settings. The M-PHY's phase-locked loop, which makes the gigabit bit clock, stops. The line drivers let go of the wires, and the receivers switch off their high-speed circuits; only a small wake-up detector stays on. Both ends go down together, because the host can't silence the chip's transmitter by itself. Coming out of hibern8 takes far less time than starting the link from scratch, because nothing has to be renegotiated.

Hibern8 is a state of the link only. Both controllers keep running, and the chip keeps VCC and VCCQ. Driven lines with termination draw current even with no data on them, which is why sleeping the link saves real power.

Two meanings

Hibern8 (say "hibernate") is not the PC kind of hibernate, where RAM is saved to disk. Only the link sleeps; the phone stays on.

Two ways in, and who brings the link back

  • Auto-hibern8 (the hardware does it). The AHIT register (offset 0x18) holds an idle time. When no command has arrived for that long, the controller takes the link down by itself. When a new command arrives (the doorbell), or when AHIT is set to 0, it brings the link back by itself. From the codeMediaTek picks the idle time by chip maker, between 1 and 3.5 ms (ufs_mtk_fix_ahit(), ufs-mediatek.c:1488).
  • Software hibern8 (the driver does it). The driver sends the UIC command DME_HIBERNATE_ENTER. The link then stays down until the driver sends DME_HIBERNATE_EXIT. In 6.6 that exit is sent by ufshcd_uic_hibern8_exit() (ufshcd.c:4413) and, on MediaTek, also by ufs_mtk_link_set_hpm() (ufs-mediatek.c:2467) inside its resume hook. Both run only when the W-LUN wakes (3.3).
Plain words

Auto-hibern8 is a motion-sensor light: it goes off when nobody's around and comes back on by itself. Software hibern8 is a light switched off by hand: it stays off until someone switches it back on.

Why writing 0 to AHIT can't wake software hibern8

Auto-hibern8 is the controller's own small state machine, and it only undoes what it did itself. Software hibern8 was entered by a command, outside that state machine, so stopping the timer has nothing to undo. And on the board, by the time the link is in software hibern8, AHIT is already 0: MediaTek's suspend hook wrote 0 before the chip went to Sleep (3.3), and nothing writes it back until the W-LUN wakes. Writing 0 again doesn't even change the register.

Why there are two kinds

  • Auto-hibern8 covers the short gaps while the disk is in use. After 1 ms of quiet the link sleeps, and the next doorbell wakes it, with no CPU, interrupt or driver code involved. Doing that in software would cost two UIC commands for every gap, each with an interrupt round trip.
  • Software hibern8 is for when more than the link goes down: the chip into Sleep, the M-PHY powered off, clocks and supplies off. Before cutting power, software must know the link is in hibern8 (it waited for the command to finish) and that it will stay there. Auto-hibern8 can promise neither.

They take turns and never overlap. The timer is off whenever software drives the link, and comes back when software hands the link back:

  • Suspend and resume: MediaTek's suspend hook turns it off (3.3), and the core writes it back as the last step of the W-LUN's wake (ufshcd.c:9999).
  • A PMC: MediaTek's pwr_change_notify turns it off before and writes it back after (ufs-mediatek.c:2023).
  • Clock gating: MediaTek lets the core enter software hibern8 during clock gating only when auto-hibern8 is disabled (ufs-mediatek.c:1779). On the board it isn't, so clock gating never uses software hibern8.

3.2 Runtime PM: who's who

Runtime PM is how Linux lets single parts of a running phone sleep while everything else keeps working. Every struct device has a usage counter and a state, active or suspended. pm_runtime_get_sync(dev) means "I need this device now": it adds 1 and, if the device sleeps, runs its wake-up function and waits. pm_runtime_put() means "I'm done"; at zero, the device may sleep after its autosuspend delay.

For UFS, Linux creates these objects:

  • The controller, hba->dev: the platform device 16810000.ufshci.
  • The SCSI host under it, and under that the LUs: sda, sdb and so on, the readable and writable slices of the chip.
  • The UFS Device W-LUN (well-known logical unit 0xD0, shown by Linux as 0:0:0:49488). It stands for the whole chip. To put the chip to sleep or wake it, the driver sends START STOP UNIT to this address.

Four rules decide who wakes whom. Each has a physical reason:

  1. Waking a device wakes its parent first. You can't reach the chip if the controller's clocks are off.
  2. Waking a parent never wakes its children. Powering the controller doesn't mean anyone needs the chip.
  3. A parent can't sleep while a child is awake.
  4. Device links add "depends on" arrows. Each LU depends on the W-LUN (device_link_add(…, DL_FLAG_PM_RUNTIME | DL_FLAG_RPM_ACTIVE), ufshcd.c:5093). So the W-LUN can't sleep while any LU is awake, and waking an LU wakes the W-LUN first.

From the codeOn the board the LUs wait 500 ms of quiet before they sleep (MTK_RPM_AUTOSUSPEND_DELAY_MS, ufs-mediatek.h:367, set at ufs-mediatek.c:1769), and the W-LUN waits 0 ms (ufshcd.c:10815). So about half a second after the last disk access, the whole chip side is asleep. That is the half second from 1.2.

Two meanings

Runtime suspend (one device sleeps while the phone is on) is not system suspend (the whole phone sleeps). This bug is entirely about runtime suspend. And ufshcd_rpm_get_sync() versus pm_runtime_get_sync() is not two mechanisms: it's the same function given a different device (2.2).

  • First version, timeout. The PMC doesn't try to wake anything; it's a negotiation.   • Second version, "exit h8 state fail". MediaTek's PRE_CHANGE hook assumes the link is either UP or in auto-hibern8; in both cases writing AHIT = 0 ends with the link UP. The function's name says the same thing: ufs_mtk_auto_hibern8_disable() turns auto-hibern8 off; leaving software hibern8 isn't its job.
  • What happened after either failure. The core marked the link broken and scheduled the error handler (ufshcd.c:4270 to 4272). The error handler wakes the W-LUN the right way, with ufshcd_rpm_get_sync() (ufshcd.c:6381), resets the controller and brings the link back at maximum gear. Key point: the rule the fix follows

Whoever calls ufshcd_config_pwr_mode() must first hold the W-LUN awake (ufshcd_rpm_get_sync()) and keep the clocks on (ufshcd_hold()). Every caller in the kernel does: MediaTek's clkscale_control path (ufs-mediatek.c:2322), the error handler (ufshcd.c:6381), and probe and reset, which run their PMC on a freshly started link. Nothing enforces it: ufshcd_config_pwr_mode() doesn't check. That's why the old code compiled and ran, and only failed in the hardware.

The deadlock that moved the job

The change is commit b294ff3e3449, "scsi: ufs: core: Enable power management for wlun", by Asutosh Das and Can Guo (both at Qualcomm). It was committed on 10 May 2021 and first released in Linux 5.14. Its commit message explains what went wrong before it:

  1. When the controller went to sleep, its own sleep function sent START STOP UNIT to the chip, to put the chip to sleep first.
  2. But by rule 3, the controller only sleeps after all its children are asleep, and that includes the SCSI devices. Their request queues were already suspended.
  3. A block-layer change, 52abca64fd94 ("scsi: block: Do not accept any requests while suspended"), made any request to a suspended queue wait until the queue resumes.
  4. So the START STOP UNIT sat waiting for a queue that would never resume, and the controller's sleep waited for the command. Nothing could move. The commit message shows the stuck call chain: ufshcd_runtime_suspend → ufshcd_suspend → ufshcd_set_dev_pwr_mode → __scsi_execute → blk_get_request → blk_queue_enter → schedule.

The fix gave the W-LUN its own runtime PM, and moved the chip-and-link work into its sleep and wake functions. With the device links (rule 4), the W-LUN sleeps after all the LUs and wakes after the controller, so its START STOP UNIT always has a working path.

3.7 Why normal disk use never hit it

Normal reads and writes come in from the bottom of the tree, and runtime PM wakes everything they depend on:

  1. A read on /dev/sda goes to that LU's queue, and the block layer wakes the LU before sending the command.
  2. The LU depends on the W-LUN through the device link (ufshcd.c:5093), so the W-LUN wakes first: hibernate-exit, chip to Active.
  3. Before that, the W-LUN's parents bring the controller up.

So every read wakes the controller, the chip and the link before its command goes out. The debugfs path came in from the top, at the controller, and waking a device never wakes anything below it.

4.3 Clock scaling, from scratch

What it is. Clock scaling switches the UFS path between two speed settings, and it moves two knobs together: the controller's clock ufs_sel (273 or 499.2 MHz, with vcore raised for the fast one) and the link's gear (the top gear, or a lower one). The reason is power: every clock tick charges and discharges millions of transistor gates, and the fast clock also needs a higher voltage, whose cost grows with the square of the voltage. An idle disk on the slow setting saves a lot.

From the codeThere are two kinds:

  • The core's automatic scaling uses Linux's devfreq with the simple_ondemand policy. Every polling period it measures what fraction of the time commands were outstanding (ufshcd.c:1535 to 1539), and scales up above a threshold and down below another. MediaTek's settings for boards that use it: poll every 200 ms, up above 40% busy, down below 20%, and the lower gear is G4 (ufs-mediatek.c:3032 to 3036). Going down it drops the gear first, then the clock; going up, the clock first, then the gear (ufshcd_devfreq_scale(), ufshcd.c:1371), so the clock is never slower than the gear needs.
  • MediaTek's manual scaling, through clkscale_control. The device tree has mediatek,ufs-clkscale-only-by-user (mt6991.dts:6768): "only by user" means only when user space asks, by writing that file. "User" here is the kernel's word for anything outside the kernel, PowerHAL included. MediaTek reads the flag into its own capability bit (ufs-mediatek.c:826) and then doesn't turn on the core's scaling (1763), so the core never calls ufshcd_devfreq_init() (ufshcd.c:8763). There is no governor on the board.

"Off" means "fixed", not "highest". With no governor, the clock stays wherever something last put it. On the board, three things put it somewhere: the core at boot, MediaTek's helper (4.4), and the ported block (4.10).

Two checks at the top: the lock and the memory

  1. The lock, clk_scale_forbid (line 2376). Writing 3 or 4 sets it, and while it's set, 1 to 4 are ignored. Writing 5 clears it. It always starts cleared after a reboot.
  2. The memory, scale_mode (lines 2380 to 2382), a static variable holding the last request. A request equal to the last one is skipped.

So 5 then 4 is enough. 5 clears the lock. And whenever scale_mode already says "up", the clocks are already fast while the disk is awake: the only thing that slows them later without touching scale_mode is MediaTek's G5 sleep hook, and its G5 wake undoes that before any command runs. When the clocks are slow while the disk is awake, scale_mode says "free run" or "down", so a 4 runs.

  • cat can lie. The store records the value you wrote even when the lock or the memory made it do nothing. Check the clocks themselves (4.11), not cat. The store accepts a powerhal_set: prefix, so PowerHAL is the obvious suspect, but that's an inference from the prefix, not something we've seen.
  • Don't write to upthreshold or downdifferential, the two files next to it. They tune the governor that doesn't exist here, and both store functions call mutex_lock(&hba->devfreq->lock) without checking for NULL. hba->devfreq is NULL on the board, so writing a number is a kernel oops. Reading them is safe.

4.5 The encryption engine

Encryption on Android has a software side and a hardware side. The hardware sits in the controller, not in the UFS chip.

  • Software. fscrypt, inside f2fs, decides which key and which per-block number each block of a file uses; Android's vold and keystore supply the keys. fscrypt can do the AES maths on the CPU, or hand it to hardware through blk-crypto. The inlinecrypt mount option chooses the hardware.
  • Hardware. From the codeAn AES engine inside the UFS host controller, defined by the UFSHCI specification. MediaTek enables it with hba->caps |= UFSHCD_CAP_CRYPTO (ufs-mediatek.c:1757) and switches it on through its secure firmware (ufs_mtk_crypto_enable(), line 258). If that call fails, MediaTek turns the capability off again (line 266), and the CPU would have to do the encryption instead. The driver loads keys into the engine's key slots and tags each request with a slot number; the engine encrypts the data as it streams out to the chip. Its clock is ufs_fde, "FDE" for full-disk encryption.
  • The chip only ever stores ciphertext. Reads of the raw device, such as dd if=/dev/block/sda, bypass the engine entirely.

4.6 Why only G5 varies: the five-part chain

At G4 with two lanes, the link tops out around 2.3 GB/s. That's below what the other four can do, so every run hits the same wall, and the G4 and G1 numbers are steady. G5 roughly doubles the link, to about 5.7 GB/s before overhead. UFS 4.0 chips are rated somewhere around 3 to 4 GB/s for sequential writes, depending on the vendor. So at G5, for the first time, the wire stops being the limit, and the next-slowest part shows through. Each of the other four can vary between runs:

  • The CPU: its frequency, and which core the fio thread lands on (4.8).
  • The encryption engine: which source its clock is on (4.4 and 4.7).
  • The controller: ufs_sel is at 499.2 MHz whenever the disk is busy at G5 (row 5 of 4.2), so it's probably not the variable one.
  • The chip: how full its fast write cache is, background work, temperature (4.9).

4.7 The most coherent story so far

Not yet provenThis story fits every row of 4.2, but it hasn't been tested. 4.11 is the test.

  1. After boot, something scales the disk down. A write of 1 to clkscale_control does exactly what was found: G4, ufs_sel at 273 MHz, the encryption clock at 416 MHz. 4.8 fio, the CPU, and a clean benchmark setup

SQPOLL

With sqthread_poll=1, a kernel thread on another CPU picks up new requests by polling, so the fio thread doesn't spend a system call on every batch. Without it, one fio thread does all the submitting and all the reaping of completions. At G5 the disk finishes a request faster than that one thread can hand it the next one, so the queue runs dry. Row 6's 600 MB/s gap was time the disk spent waiting for fio.

  • To confirm: fio prints cpu: usr=…, sys=… for each job. If they add up to nearly 100% without SQPOLL, that thread is the limit.
  • Other ways to the same result: bigger blocks (bs=1m, fewer requests per GB), a deeper queue, numjobs=2, or fio pinned to a big core (cpus_allowed).
  • SQPOLL is a workaround for a host-side limit. The Qualcomm SoC runs probably didn't need it because the disk was the slow part there: at G4 or below the link caps everything near 2 GB/s, long before the CPU matters. Whatever you choose, keep the fio settings identical on both platforms.

The settings that remove noise

  • The prep script, every session. echo 0 0 0 > /proc/sys/kernel/printk stops kernel messages from going to the serial console, which is very slow and can stall a CPU for milliseconds; dmesg still records everything. Turning tracing off removes per-event recording. The performance governor keeps the CPUs at full speed, which matters most here, because the CPU can be the limit at G5.
  • power/control = on for the W-LUN while hunting. The chip side never sleeps: no wake-up cost at the start of a run, no G5 clock dip, and the chip can flush its write cache between runs. Phones run with auto, so once the cause is known, also measure with auto and report both.
  • Clock gating off is optional. It only acts after 10 ms with nothing in flight, which never happens during a streaming run. Turning it off removes one more variable and costs only idle power (clkgate_enable; writing 0 makes the core hold the clocks permanently).
  • No keep-alive I/O. A running benchmark keeps the disk awake by itself; the clock only drops after 500 ms with no I/O at all. A second job shares the link with the benchmark, so the number would depend on what the other job is doing.
  • Long enough runs. 4 GB at about 3.3 GB/s is only about 1.2 seconds, so startup is a noticeable share. Use bigger runs, but for writes keep each one below the free WriteBooster space, and start every run from the same cache state (4.9).

4.9 WriteBooster: the chip's fast write cache

WriteBooster is a region of the chip's flash run in a fast mode (one bit per cell). Writes land there first, and later the chip flushes them into normal, denser flash, freeing the space again. While the cache has room, writes are fast; when it fills, writes go straight to the slower flash.

From the codeWhy the WriteBooster cache doesn't refill while the board is idle:

  • The chip needs VCC to flush. The core says so in a comment in ufshcd_wb_need_flush(): "The ufs device needs the vcc to be ON to flush".
  • At 500 ms idle the W-LUN sleeps, the chip goes to Sleep and VCC goes off (3.4), unless the core decides a flush is needed. In that case it keeps the chip Active and VCC on during the sleep (ufshcd.c:9820 to 9825).
  • "Needed" means 10% or less of the cache available in user-space-reduction mode (ufshcd.c:6189), or below wb_flush_threshold, 40% by default, in preserve-user-space mode (ufshcd.c:9086).
  • With about 40 GB free the chip is above both, so the chip sleeps instead of flushing. Nothing we changed touches this.
Try it: read the cache state 
U=/sys/bus/platform/devices/16810000.ufshci
cat $U/wb_on $U/enable_wb_buf_flush $U/wb_flush_threshold
cat $U/flags/wb_enable $U/flags/wb_flush_en $U/flags/wb_flush_during_h8
cat $U/attributes/wb_avail_buf $U/attributes/wb_cur_buf $U/attributes/wb_flush_status

wb_avail_buf counts in tenths: 10 means 100% free, 4 means 40%. Read it before and after one 4 GB write. If it never drops, WriteBooster may not be in use at all (wb_on or wb_enable at 0), and the writes are going straight to the slower flash. To let the chip flush between runs, keep power/control = on and wait: with the chip powered and the link only in auto-hibern8, it can flush if wb_flush_during_h8 is 1, and wb_avail_buf should climb back.

4.10 The ported clock-scaling block on the board

From the codeThe block decides "scale up" for any gear above G1 and calls ufshcd_scale_clks(), around the PMC. That function has two halves. MediaTek's half, which raises vcore first and then switches sources, returns at once because core scaling is off (ufs_mtk_clk_scale_notify(), ufs-mediatek.c:3172). The core's half, ufshcd_set_clk_freq() (ufshcd.c:1066), calls clk_set_rate() on every clock with a frequency entry, which on the board means ufs_sel only, and skips it when the core's record, clki->curr_freq, already matches.

Seen on the boardA G1 visit sets ufs_sel to 273 MHz. The next gear-up sets it to 499.2 MHz. At G4 it then stays at 499.2 MHz, because MediaTek's sleep and wake hooks only touch the clocks at G5, and nothing else lowers it (rows 3 and 4 of 4.2).

Is 499.2 MHz at G4 unsafe? It depends on history, because the block never touches vcore:

  • If the disk last woke at G5, MediaTek's resume hook asked for 0.65 V, and nothing at G1 to G4 releases that. Then 499.2 MHz at G4 has its voltage, and the only cost is wasted power: MediaTek runs G4 at 273 MHz.
  • If MediaTek's scale-down ran since then, the 0.65 V request was released, and 499.2 MHz runs without it, a pairing MediaTek's own code never allows.
Try it: is the vcore floor held? 
grep -i ufshci /sys/kernel/debug/regulator/regulator_summary

On the controller's dvfsrc-vcore line, 650mV 2147483mV means the floor is held; 0mV … means it's released.

Why delete it. For G2 to G5 it either does nothing or undoes its own G1 change. Its one real action, clk_set_rate(ufs_sel, 273 MHz) at G1, is the call MediaTek's design avoids (4.4): the clock framework picks the source by itself, which MediaTek's flow never exercises. It can't move the encryption clock, which is the one that matters for G5 writes to /data. And dropping it costs nothing: a slow link with the fast controller clock is the normal state during every boot, because the core sets 499.2 MHz before the link starts. File 07 drops it.

Plain words

"Don't gear changes need clock scaling?" Only if something can lower the clock. The rule only works one way: the controller's clock must never be slower than the gear needs, and faster is always fine. On the board three things lower it: this block (at G1), clkscale_control 1 or 3, and MediaTek's own sleep at G5, which its wake undoes. The block creates the very need it then fills.

4.11 The decisive run

One run with everything fixed separates the encryption clock from the CPU:

Try it 
sh mtk_prepare.sh
echo on > /sys/bus/scsi/devices/0:0:0:49488/power/control
echo 0  > /sys/bus/platform/devices/16810000.ufshci/clkgate_enable
C=/sys/bus/platform/devices/16810000.ufshci/clkscale/clkscale_control
echo 5 > $C; echo 4 > $C
grep -w -B8 ufs_fde /sys/kernel/debug/clk/clk_summary   # walk up to ck_aes_ufsfde_sel

The encryption clock must read 546000000, under ck_mainpll_d4, every time you look: with the chip side never sleeping, there is no more hopping. Append these lines to mtk_prepare.sh, so a reboot doesn't lose them. Then run the 10 G5L2 ↔ G1L2 iterations, and once, read the encryption clock in the middle of a write (fio in the background, wait a second, then the grep).

4.12 Permanent fixes, if the encryption clock is confirmed

  • A boot step: echo 5, then echo 4, to clkscale_control. It puts vcore and both clocks on their fast settings and locks out later scale-downs. It holds even with power/control = auto: a G5 sleep drops the clocks, but the G5 wake restores them before any command, and gear changes through power_mode never lower the encryption clock. The simplest fix, and no rebuild.
  • A change in MediaTek's vendor module. The clean one: when a power mode change targets G5, call _ufs_mtk_clk_scale(hba, true) first, the way MediaTek's own clkscale_control path does before its PMC to the maximum gear. A smaller alternative: run the helper once at init, so the encryption clock never sits on the bootloader's choice. Either needs a vendor-module rebuild.
  • The vendor-side route. File 02, ufs_mtk_config_gear_lane(), already calls _ufs_mtk_clk_scale(hba, true) before a G5 change. It was never wired in, because the debugfs file lives in the core.

The core can't do it by itself: _ufs_mtk_clk_scale() is private to MediaTek's module, and the core doesn't even know the encryption clock has two speeds.

4.13 Where a patch could go

  • The board's own vendor tree: the realistic first step, once file 07 is built and tested.
  • Mainline Linux: possible, but it would be a new feature. Mainline 6.18 has no way to change gear or lanes at runtime, only the read-only power_info/gear and lane files. A patch would need to be written against current mainline, not 6.6; to use a core helper like Part A of file 07 instead of exporting internals; and to explain what happens on boards where the governor would undo the gear.
  • The Android common kernel: takes it only after it's upstream.
  • MediaTek: two small, concrete reports. The upthreshold and downdifferential NULL-pointer crash, in a vendor file mainline doesn't have (fix: return -EOPNOTSUPP when hba->devfreq is NULL). And, if 4.11 confirms it, the encryption clock left on its slow source until the first scale-up, even though MediaTek's init comments that the default is the maximum frequency.

6Command cheat sheet

Every board command from this document, in one place. Set these once per shell:

U=/sys/bus/platform/devices/16810000.ufshci                 # the controller
W=/sys/bus/scsi/devices/0:0:0:49488                         # the UFS Device W-LUN
C=$U/clkscale/clkscale_control                              # MediaTek's clock control
P=/sys/kernel/debug/ufshcd/16810000.ufshci/power_mode       # the debugfs file (adjust)
D=/sys/kernel/debug/ufshcd/16810000.ufshci                  # the core's debugfs directory
K=/sys/kernel/debug/clk

Read the state

cat $P                                         # gear, lanes, mode the core recorded
cat $W/power/runtime_status                    # active or suspended (the chip side)
cat $W/power/control                           # auto or on
grep -w -B8 ufs_sel $K/clk_summary             # walk up to ck_sel: 273000000 or 499200000
grep -w -B8 ufs_fde $K/clk_summary             # walk up to ck_aes_ufsfde_sel: 416000000 or 546000000
cat $K/ck_sel/clk_rate $K/ck_sel/clk_parent
cat $K/ck_aes_ufsfde_sel/clk_rate $K/ck_aes_ufsfde_sel/clk_parent
grep -i ufshci /sys/kernel/debug/regulator/regulator_summary   # vcore request: 650mV or 0mV
cat $D/stats                                   # error counters (PA, DL, resets ...)
cat $C                                         # current: N (can lie, see 4.3)
cat $U/clkgate_enable $U/clkgate_delay_ms      # clock gating
cat $U/attributes/wb_avail_buf $U/attributes/wb_cur_buf $U/attributes/wb_flush_status
cat $U/flags/wb_enable $U/flags/wb_flush_en $U/flags/wb_flush_during_h8
cat $U/wb_on $U/enable_wb_buf_flush $U/wb_flush_threshold
cat $U/device_descriptor/specification_version
ls /sys/class/devfreq/; ls $U/clkscale_enable  # automatic scaling present?
mount | grep " /data "                         # inlinecrypt?
dmesg | grep -E "exit h8|PMC Success|err_handler started|query device ref clk|crypto enable failed"

Change settings

sh mtk_prepare.sh                     # printk quiet, tracing off, performance governor
echo on   > $W/power/control          # chip side never sleeps   (auto = default)
echo 0    > $U/clkgate_enable         # clock gating off          (1 = default)
echo 5 > $C; echo 4 > $C              # both clocks fast, vcore up, max gear, locked
echo 552211 > $P                      # G5, 2 lanes, FAST   (112211 = G1, 442211 = G4)

Benchmark

echo 3 > /proc/sys/vm/drop_caches     # before buffered tests
fio --name=g5read --filename=/dev/block/sda --readonly --rw=read --direct=1 \
    --ioengine=io_uring --sqthread_poll=1 --bs=1m --iodepth=32 \
    --runtime=20 --time_based --ramp_time=2
fio --name=g5write --filename=/data/local/tmp/fio.bin --rw=write --size=8g \
    --direct=1 --ioengine=io_uring --sqthread_poll=1 --bs=1m --iodepth=64 --end_fsync=1
dd if=/dev/block/sda of=/dev/null bs=1M count=8192    # quick raw read
Watch out
  • Never write to the raw device (/dev/block/sda): it holds your partitions. Use --readonly for raw reads, and a file in /data for writes.
  • Never write to $U/clkscale/upthreshold or downdifferential on this board (4.3).
  • A reboot resets power/control, clock gating, the CPU governor and MediaTek's lock. Keep them in mtk_prepare.sh.

7Glossary

ADAPT
UniPro's equalization training: when the link enters G4 or G5, both ends tune their transmitters and receivers to the wire. MediaTek asks for the full version, PA_INITIAL_ADAPT, on every change into those gears.
AH8 (auto-hibern8)
The controller takes the link into hibern8 by itself after an idle time, and brings it back by itself on the next command or when AHIT is set to 0.
AHIT
The controller register (offset 0x18) holding the auto-hibern8 idle time. 0 means off. 1 ms on the board.
blk-crypto
The block layer's interface to inline encryption hardware: requests carry a key and a per-block number that the driver passes to the engine.
clk_scale_forbid
MediaTek's lock, set by clkscale_control 3 and 4 and cleared by 5. While it's set, MediaTek's own clock and gear changes are skipped.
clkscale_control
MediaTek's sysfs file for manual clock scaling, values 0 to 5 (4.3).
Clock gating
Switching the controller's clocks off after a short idle time (10 ms on MediaTek) and back on before the next command. Separate from runtime PM and from clock scaling.
Clock scaling
Moving the controller's clock and the link's gear between a fast and a slow setting, to save power. Automatic (devfreq) or manual (clkscale_control). Only the manual kind exists on the board.
curr_freq
The core's record of each scalable clock's rate. MediaTek's own clock moves don't update it, which is how the core's record and the real clock can disagree.
Device link
A "depends on" arrow between two Linux devices. Each LU depends on the W-LUN, so waking an LU wakes the W-LUN first.
devfreq
Linux's framework for changing a device's frequency according to load. It drives the core's automatic UFS clock scaling. Never started on the board.
DME
The part of UniPro that takes management commands: DME_GET, DME_SET, DME_HIBERNATE_ENTER, DME_HIBERNATE_EXIT.
Doorbell
Controller register (offset 0x58) with one bit per command slot.
EH (error handler)
The core's recovery work. It resets the controller, restarts the link and restores the maximum gear.
f2fs
The flash-friendly filesystem Android uses for /data.
FDE, ufs_fde
The clock of the controller's inline AES engine (ck_aes_ufsfde_sel), 416 or 546 MHz. "FDE" stands for full-disk encryption.
fscrypt
The kernel's file-based encryption, used by Android for /data. It can encrypt on the CPU or through inline hardware.
Gear
Bits per second per lane. HS-G1 to G5 are the fast family, each double the last.
GKI
Android's Generic Kernel Image, the common kernel that holds the UFS core.
hba
The core's struct ufs_hba, describing one controller. hba->dev is the controller's struct device.
Hibern8
The link's deepest sleep that keeps its settings. Entered by the AHIT timer (auto) or by a command (software).
host_sem
The core's semaphore that keeps user requests, error handling, system suspend and shutdown from overlapping.
inlinecrypt
The mount option that makes fscrypt use the inline encryption hardware.
Lane
One pair of wires carrying data in one direction.
LU
Logical unit: a readable, writable slice of the chip (sda, sdb, …).
M-PHY
The electrical layer: the wires, their voltages, and recovering bits and timing from them.
MTCMOS
MediaTek's name for a switchable power domain inside the SoC. MediaTek switches off the UFS controller's domain after the controller sleeps.
Mux
A clock multiplexer: it outputs one of several source clocks. ck_sel and ck_aes_ufsfde_sel are muxes with two sources each.
Only by user
The device-tree flag mediatek,ufs-clkscale-only-by-user: clock scaling happens only when user space writes clkscale_control.
PACP
Control frames sent by UniPro's lowest layer. A PMC is a PACP_PWR_req from the host and a PACP_PWR_cnf back from the chip.
PMC
Power mode change: switching gear, lanes or mode.
PMIC
The power-management chip (MT6363 here) whose regulators make the board's supply rails.
Power level (rpm_lvl)
The core's pairing of a chip power mode and a link state, from ufs_pm_lvl_states[]. The board's runtime level 3 is {Sleep, hibern8}.
PowerHAL
Android's power service. It may write clkscale_control with a powerhal_set: prefix; not confirmed on the build.
Rate A, rate B
The two base frequencies for HS gears. MediaTek uses B.
Reference clock
The steady clock the host supplies to the chip's side of the link. MediaTek stops it once the link is in hibern8.
Runtime PM
Linux's per-device sleep and wake while the system is running.
scale_mode
MediaTek's static memory of its last clock-scaling request. A repeat of the same request is skipped.
setup_clocks
The vendor hook the core calls whenever it turns the controller's clocks on or off.
SMC
Secure monitor call: asks the secure firmware to do something Linux can't do directly. MediaTek uses SMCs for the UFS SRAM and the encryption engine.
SQPOLL
An io_uring mode (fio sqthread_poll=1) where a kernel thread picks up new requests by polling, saving the application a system call per batch.
SRAM
On-chip memory. The UFS controller has a block of it, switched off when the chip side sleeps.
SSU (START STOP UNIT)
The SCSI command that sets the chip's power mode: Active, Sleep, PowerDown, DeepSleep. It cuts no power by itself.
Symbol clock
A clock running at the link's own rate: unipro_tx_sym for sending, and one receive clock per lane.
UIC command
A command for the link layer, written to controller register 0x90.
uic_link_state
The core's record of the link state. Only software moves update it; auto-hibern8 doesn't.
UniPro
The link layer: frames, acknowledgements, resending, speed and power state.
UniPro power-down
MediaTek's attribute VS_UNIPROPOWERDOWNCONTROL (0xD0A8), set to 1 when the chip side sleeps, so the host's UniPro engine stops.
UPIU
The packet format that carries SCSI commands over UFS.
VCC
The supply rail for the chip's flash. The host switches it off once the chip is in Sleep.
VCCQ
The 1.2 V supply rail for the chip's controller and its end of the link. Low-power mode during runtime sleep, never off.
vcore
The SoC's core supply voltage. The 499.2 MHz ufs_sel source needs at least 0.65 V.
vops
The table of vendor hooks the core calls (pwr_change_notify, suspend, resume, setup_clocks, …).
W-LUN
Well-known logical unit. The UFS Device W-LUN (0xD0, shown by Linux as 0:0:0:49488) stands for the whole chip.
WriteBooster
The chip's fast write cache, flushed later into normal flash. It needs VCC to flush.
