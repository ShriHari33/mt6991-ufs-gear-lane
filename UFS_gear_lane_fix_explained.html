Changing UFS gear and lanes at runtime on MT6991

Why the debugfs write failed with “exit h8 state fail”, and why one line fixed it. Explained from scratch.

Written 31 October 2026, updated 1 November 2026 · MediaTek MT6991 SoC evaluation board · Android GKI kernel 6.6 (android15-6.6) with MediaTek vendor modules
The whole story in six lines
  1. The board's kernel has a debugfs file, power_mode. Writing six digits to it (for example 332211) should change the speed (gear), width (lanes) and mode of the link between the processor and its UFS storage chip.
  2. The write woke up the UFS controller inside the processor, but not the UFS chip. The link between them stayed in hibern8, its deep-sleep state.
  3. Before any speed change, MediaTek's driver checks that the link is awake. It waited 100 ms, the link never woke, and it printed exit h8 state fail.
  4. The fix was one call: ufs_debugfs_get_user_access(), which runs ufshcd_rpm_get_sync(), instead of pm_runtime_get_sync(hba->dev). The new call wakes the chip side too.
  5. The old line was correct in Linux 4.19, where the ported code came from. In Linux 5.14 (2021) the job of waking the link moved to a different object, so the same line now does less.
  6. Result on the board, 31 October: no more failures, and lane changes work.

1The hardware: two chips and some wires

1.1 What is physically on the board

Two chips matter here.

  • The MT6991 processor (the SoC). Besides the CPU cores, it contains a block of logic called the UFS host controller. In this document it's the controller.
  • The UFS storage chip. NAND flash memory plus its own small processor that manages the flash. In this document it's the chip.

Copper traces on the circuit board connect the two. These traces are the lanes. A lane carries bits in one direction only. Each lane is a pair of wires, and a bit is sent as the voltage difference between them: one wire goes up while the other goes down. Noise that hits both wires equally cancels out, which is why this works at billions of bits per second. MT6991 uses two lanes from the controller to the chip (transmit, TX) and two lanes back (receive, RX). That's eight data wires. The standard that defines these wires and their voltages is called M-PHY.

The CPU talks to the controller through registers. A register is a memory address wired to hardware instead of to RAM. Writing a number there makes the hardware do something; reading it tells you what the hardware is doing. The controller's registers start at physical address 0x16810000, the ufshci@16810000 node in the device tree (mt6991.dts:6686). Four of them matter in this story (offsets from that base):

OffsetNameWhat it does
0x18AHIT (auto-hibernate idle timer)How long the link may sit idle before the controller puts it to sleep by itself. Writing 0 turns this off. (Part 2.)
0x58Transfer request doorbellOne bit per command slot. The driver sets a bit to say “slot n has a command, go”; the controller clears it when the command is done.
0x90UIC commandWhere the driver writes commands for the link itself: wake it, put it to sleep, read or change a link setting.
0x14CMediaTek link state (REG_UFS_UFS_MMIO_OTSD_CTRL)MediaTek-specific. Its top byte says whether the link is up, down or asleep. (Part 2.)
Two meanings

“Host” can mean the controller hardware, Linux's SCSI host object (struct Scsi_Host), or loosely the whole phone. “Device” can mean the UFS chip, or any struct device in Linux's tree of objects. In this document, the controller and the chip are always the hardware. A plain “device” means the Linux object.

The chip runs on two supply rails. They come from the PMIC, a separate power-management chip on the board (an MT6363 here), which the processor commands:

Only the host switches these rails; the chip has no say. All the chip gets is a warning first (START STOP UNIT, Part 3). Section 3.6 shows the moment each rail changes.

1.2 Three layers of rules on the wires

Wires alone aren't enough; both ends need rules. UFS stacks three sets of them, and the chip runs the same stack on its side:

UFS transport (UTP)Carries SCSI commands (READ, WRITE, START STOP UNIT, …) in packets called UPIUs. This is what the files are made of.
UniProThe link layer. Packs bits into frames, checks them, acknowledges them and re-sends anything lost. It also owns the link's speed and power state. Its settings are numbered attributes, such as PA_TXGEAR (0x1568, the transmit gear) or PA_ACTIVETXDATALANES (0x1560, how many transmit lanes are in use). “PA” stands for PHY Adapter, the bottom part of UniPro.
M-PHYThe electrical layer: drives the voltages, recovers bits and timing at the other end, puts the wires to sleep and wakes them.

The driver reaches UniPro through UIC commands, written to register 0x90. The ones in this story are DME_GET and DME_SET (read or write one attribute), and DME_HIBERNATE_ENTER and DME_HIBERNATE_EXIT (put the link to sleep, wake it up). DME is the part of UniPro that accepts these commands (the Device Management Entity).

Plain words

SCSI is what the letter says. UniPro is the delivery service that numbers the letters, confirms delivery and re-sends lost ones. M-PHY is the road.

1.3 Gears: how fast the wires flip

A gear is how many bits per second each lane carries. The high-speed (HS) gears go from G1 to G5, and each gear doubles the one before. There are two slightly different base frequencies, called rate A and rate B. MediaTek always uses rate B (it's the default, PA_HS_MODE_B, in the core's shared negotiation helper).

GearBits per second per lane (rate B)One bit lasts
HS-G11,457.6 million686 ps
HS-G22,915.2 million343 ps
HS-G35,830.4 million172 ps
HS-G411,660.8 million86 ps
HS-G523,321.6 million43 ps

To make that physical: at G5 one bit lasts 43 picoseconds (trillionths of a second). In that time a signal travelling along a circuit-board trace covers about 6 or 7 millimetres.

Not every bit on the wire is your data. Gears G1 to G4 send every 8 bits of data as 10 bits on the wire (8b/10b encoding), which keeps the signal balanced and lets the receiver stay locked to its timing. G5 uses the more efficient 128b/130b. So the data a lane can carry is its bit rate × 0.8 (× 128/130 at G5). Part 8 uses this to check that a gear change really happened.

There is also a slow family, the PWM gears, used for bring-up and low power. They run from a few megabits per second to a few hundred.

The controller's own clock has to keep up with the gear. On MT6991 that clock is ufs_sel, which switches between a 273 MHz source and a 499.2 MHz source (freq-table-hz = <273000000 499200000>, mt6991.dts:6732). MediaTek's code pairs the top gear with 499.2 MHz and G4 with 273 MHz (section 6.4). The 499.2 MHz source needs the SoC's core supply voltage (vcore) at 0.65 V or more (clk-scale-up-vcore-min = <650000>, mt6991.dts:6751).

Added 1 Nov · The clock rule only works one way

“Has to keep up” means the controller's clock must never be slower than the gear needs. Faster is always fine; slowing it down at low gears only saves power.

  • The gear alone sets the wire speed. A PMC sets PA_TXGEAR, and the M-PHY switches its line rate. The link has its own clocks for that, listed in the device tree as unipro_tx_sym, unipro_rx_sym0 and unipro_rx_sym1 (mt6991.dts:6723). There is one receive clock per lane because each lane's receiver recovers its timing from the bits arriving on it.
  • ufs_sel is the controller's clock (mt6991.dts:6717): it sets how fast the controller can move data between memory and the link. A fast controller in front of a slow link just waits more.
  • Every boot already does this. The core sets ufs_sel to 499.2 MHz in ufshcd_init_clocks() (ufshcd.c:9398) before the link starts, and the link then runs its first commands in PWM-G1, the slowest mode there is.
  • G1 to G3. MediaTek's code never chooses G2 or G3; the only lower gear it picks on its own is G4, on the 273 MHz source. Each gear doubles the one before, so G1 to G3 carry less than G4. 273 MHz is enough for them, and 499.2 MHz is more than enough for every gear.
  • vcore follows the clock, not the gear. 499.2 MHz needs at least 0.65 V at any gear; 273 MHz doesn't. MediaTek's helper _ufs_mtk_clk_scale() (ufs-mediatek.c:3039) always moves the two together: vcore up before the clock goes up, and down only after the clock comes down.

The one place MediaTek itself runs HS-G1 is its eye-monitor and scrambler debug code (ufs-mediatek-sysfs.c:307 and 614), and there it uses the 273 MHz source. Section 6.3 uses this rule.

1.4 Lanes

Lanes are parallel roads. With two lanes the data is split across both, so the link carries twice as much. Each direction can use 1 or 2 lanes.

Two meanings

“Two lanes” in UFS means two per direction: 2 TX and 2 RX, four wire pairs. In the six digits, the lane part 22 is one digit for RX and one for TX.

1.5 Modes: the last two digits

  • 1 = FAST_MODE: the HS gears.
  • 2 = SLOW_MODE: the PWM gears.
  • 4 = FASTAUTO, 5 = SLOWAUTO: the same, except that the link may drop into a lower-power state on its own between bursts of data.
Two meanings: “power mode” has three
  1. Link power mode (UniPro): FAST, SLOW, FASTAUTO, SLOWAUTO. The link's speed setting. The digits set this.
  2. Chip power mode: Active, Sleep, PowerDown. Set by sending the chip the SCSI command START STOP UNIT (often shortened to SSU).
  3. Linux runtime PM state of a struct device: active or suspended (Part 3).

The bug involved all three at once.

1.6 A power mode change, step by step

Changing gear, lanes or mode is a power mode change, or PMC. Both ends must switch at the same moment, so a PMC is a conversation over the link:

  1. The driver writes the new settings into the controller's UniPro attributes: PA_RXGEAR, PA_ACTIVERXDATALANES, PA_RXTERMINATION, PA_TXGEAR, PA_ACTIVETXDATALANES, PA_TXTERMINATION, PA_HSSERIES (rate A or B), and some timeout values (PA_PWRMODEUSERDATA0 and onwards).
  2. It writes PA_PWRMODE. That write is the trigger.
  3. UniPro negotiates the change with the chip, over the link.
  4. The controller raises an interrupt with the result. “Local success” means done.

In the 6.6 code, ufshcd_change_power_mode() (ufshcd.c:4560) does steps 1 and 2, and ufshcd_uic_pwr_ctrl() (ufshcd.c:4199) waits up to 500 ms (UIC_CMD_TIMEOUT_DEFAULT) for step 4. If nothing arrives, it prints pwr ctrl cmd 0x… with mode 0x… completion timeout (ufshcd.c:4237).

Key point

A PMC is a conversation over the link. If the link is asleep, nobody answers.

The six digits are GGLLMM: gear RX, gear TX, lanes RX, lanes TX, mode RX, mode TX. So 332211 means HS-G3, two lanes each way, FAST mode.

2Sleep: what hibern8 is

2.1 The link's deep sleep

When there's nothing to send, keeping eight wires switching billions of times a second wastes power. Hibern8 (say “hibernate”) is the link's deepest sleep that still remembers its settings. The transmitters stop driving the wires, and the circuits that generate the fast clocks (the PLLs) stop. The gear and lane settings are kept, so waking up is much quicker than starting the link from scratch.

Two meanings

Hibern8 is not the PC kind of hibernate, where RAM is saved to disk. Only the link sleeps; the phone stays on.

2.2 Two ways in, and one way out of each

Auto-hibern8 (AH8): the hardware does it. You put an idle time into the AHIT register (offset 0x18). If no command arrives for that long, the controller puts the link to sleep by itself, and when a new command arrives it wakes the link by itself. Software takes no part. MediaTek sets the idle time according to who made the chip: 3.5 ms for Samsung, 2 ms for Micron, 1 ms for everyone else (ufs_mtk_fix_ahit(), ufs-mediatek.c:1488). Writing 0 to AHIT turns the timer off.

Software hibern8: the driver does it. The driver sends the UIC command DME_HIBERNATE_ENTER. The link then stays asleep until the driver sends DME_HIBERNATE_EXIT. The hardware will not wake it on its own, and changing AHIT doesn't touch it.

Plain words

Auto-hibern8 is a motion-sensor light: it goes off when nobody's around and comes back on when someone walks in. Software hibern8 is a light somebody switched off by hand: it stays off until somebody switches it back on.

Key point

The whole bug in one sentence: MediaTek's check treated a hand-switched light as if it were a motion-sensor light, and waited for it to come on by itself.

Added 1 Nov · Why writing 0 to AHIT can't wake software hibern8
  • Auto-hibern8 is the controller's own small state machine. The timer runs out and the controller takes the link down; a doorbell, or AHIT going to 0, makes it bring the link back. It only undoes what it did itself.
  • Software hibern8 sits outside that state machine. A UIC command, DME_HIBERNATE_ENTER, took the link down, and only the opposite command brings it back. In 6.6 that's sent by ufshcd_uic_hibern8_exit() (ufshcd.c:4413) and, on MediaTek, also by ufs_mtk_link_set_hpm() (ufs-mediatek.c:2467) in its resume hook. Both run only when the W-LUN wakes.
  • On the board AHIT is already 0 by then. MediaTek's suspend hook writes 0 before the chip goes to Sleep (3.4), and nothing writes it back until the W-LUN wakes. Writing 0 again doesn't even change the register, so the controller has nothing to react to.
  • Both ends of the link go down, not the chip. Hibern8 also takes down the chip's transmitters and receivers, its half of the lanes. The chip itself keeps running: its controller is on, and VCC and VCCQ stay on.

Why there are two kinds

They do different jobs on different time scales:

  • Auto-hibern8 covers the short gaps while the disk is in use. After 1 ms of quiet the controller takes the link down, and the next doorbell brings it back, with no CPU, interrupt or driver code involved. Doing that in software would take two UIC commands for every gap, each with an interrupt round trip.
  • Software hibern8 is for when more than the link goes down: the chip into Sleep, the M-PHY powered off, clocks off. Before cutting power, software must know the link is in hibern8 (it waited for the command to finish) and that it will stay there. Auto-hibern8 can promise neither: the link can be up or down at any moment, and the next doorbell wakes it.

They take turns and never overlap. The timer is off whenever software drives the link, and it comes back when software hands the link back:

  • Suspend and resume: MediaTek's suspend hook turns it off (3.4), and the core writes it back as the last step of the W-LUN's wake (ufshcd.c:9999).
  • A PMC: MediaTek's pwr_change_notify turns it off before and writes it back after (ufs-mediatek.c:2023).
  • Clock gating: MediaTek lets the core enter software hibern8 during clock gating only when auto-hibern8 is disabled (ufs-mediatek.c:1779). On the board it isn't, so clock gating never uses software hibern8.

3The software: who's who in Linux

3.1 Core and vendor: where the ported code runs

On Android, Google builds one generic kernel image for every phone, the GKI (Generic Kernel Image). The UFS core is part of it: drivers/ufs/core/ufshcd.c, ufs-debugfs.c and their friends. MediaTek's UFS code (ufs-mediatek.c, ufs-mediatek-sysfs.c, …) is a vendor module loaded on top, from kernel_device_modules.

The core calls into the vendor module through vops (“variant operations”): a table of function pointers that MediaTek fills in. The ones in this story are:

  • pwr_change_notify, called just before a PMC (PRE_CHANGE) and just after it (POST_CHANGE);
  • suspend and resume, called when the chip side goes to sleep or wakes;
  • clk_scale_notify, called around clock changes.

The debugfs file lives in the core's ufs-debugfs.c. It can call core functions, but it can't see MediaTek's private data (struct ufs_mtk_host). That's why the fix had to use a core helper. It's also why a change there needs a new kernel image, not just a new vendor module.

Added 1 Nov · Which side calls suspend and resume

The hooks' names don't say whose suspend they mean. In 6.6, suspend and resume are called by the W-LUN, the chip side:

  • __ufshcd_wl_suspend() calls suspend twice: PRE_CHANGE at ufshcd.c:9830 and POST_CHANGE at 9879.
  • __ufshcd_wl_resume() calls resume at ufshcd.c:9939.

Up to Linux 5.13 the controller's own ufshcd_suspend() called the same hook (ufshcd_v5.13.c:8769). The name stayed the same and the caller moved, together with the job (Part 4).

The controller's own sleep and wake give the vendor a different hook, setup_clocks, called from ufshcd_setup_clocks() (ufshcd.c:9298 and 9329). It runs when the controller sleeps or wakes (10136, 10176), and also on every clock gate and ungate (1910, 1768). Sections 3.4 and 3.6 say what MediaTek does in each.

Two meanings: debugfs and sysfs

Both are files the kernel invents on the fly. sysfs (/sys) is the stable interface for real users; MediaTek's clkscale_control lives there. debugfs (/sys/kernel/debug) is for developers and can change at any time; the power_mode file lives there.

3.2 The objects Linux creates for UFS

Linux keeps a tree of struct device objects, one for each thing it manages. For UFS the tree looks like this:

  • hba->dev is the controller, as a “platform device” named 16810000.ufshci. Its jobs: the controller's clocks, interrupt and power supplies. (hba stands for host bus adapter, the core's struct ufs_hba for one controller.)
  • host0 is Linux's SCSI host. The chip speaks SCSI, so Linux handles it like a SCSI disk enclosure.
  • Logical units (LUs) are slices of the chip that you can read and write. They appear as sda, sdb, sdc, and so on; your partitions live inside them.
  • Well-known logical units (W-LUNs) are special addresses for jobs that concern the whole chip. The important one is the UFS Device W-LUN: to put the whole chip to sleep or wake it, you send START STOP UNIT to this address.

The UFS Device W-LUN is number 0xD0 in UFS's own numbering. Linux shows it as 0:0:0:49488. The arithmetic: clear the W-LUN flag bit (0x80), which leaves 0x50; add SCSI's base for well-known units, 0xC100; that gives 0xC150, which is 49488. (The RPMB W-LUN, 0xC4, becomes 49476, and the BOOT W-LUN, 0xB0, becomes 49456.)

Plain words

The W-LUN is Linux's handle on the chip itself. Waking the W-LUN means waking the chip and the link that leads to it.

3.3 Runtime PM from scratch

Runtime PM is how Linux lets single parts of a running phone sleep while everything else keeps working. Every struct device has a usage counter and a state, active or suspended.

  • pm_runtime_get_sync(dev) means “I need this device now”. It adds 1 to the counter. If the device is asleep, it runs the device's wake-up function (its resume callback) and waits for it to finish.
  • pm_runtime_put(dev) means “I'm done”. It subtracts 1. At zero, the device may go to sleep after its autosuspend delay.

Four rules decide who wakes whom. Each has a physical reason:

  1. Waking a device wakes its parent first. You can't reach the chip if the controller's clocks are off.
  2. Waking a parent never wakes its children. Powering the controller doesn't mean anyone needs the chip.
  3. A parent can't sleep while a child is awake.
  4. Device links add “depends on” arrows. Each LU depends on the W-LUN (device_link_add(…, DL_FLAG_PM_RUNTIME | DL_FLAG_RPM_ACTIVE), ufshcd.c:5093). So the W-LUN can't sleep while any LU is awake, and waking an LU wakes the W-LUN first.

On the board the LUs wait for 500 ms of quiet before they sleep (MTK_RPM_AUTOSUSPEND_DELAY_MS, ufs-mediatek.h:367, set as the SCSI host's rpm_autosuspend_delay at ufs-mediatek.c:1769), and the W-LUN waits 0 ms (ufshcd_wl_probe(), ufshcd.c:10815). So about half a second after the last disk access, the whole chip side is asleep.

Step 1: why the timer goes off first

From step 1 on, software drives the link by itself, and it needs the link in a known state:

  • START STOP UNIT travels over the link, so the link must be UP to carry it. MediaTek's ufs_mtk_auto_hibern8_disable() (ufs-mediatek.c:2997) writes 0 to AHIT, waits up to 5 ms for the controller's state machine to go idle, then waits up to 100 ms for register 0x14C to say UP.
  • The core can't see auto-hibern8. hba->uic_link_state changes only when software moves the link (ufshcd.c:1905 in clock gating, 9608 in ufshcd_link_state_transition()). When the timer takes the link down, that variable still says ACTIVE. __ufshcd_wl_suspend() checks that the link is active before it starts (9784), but with the timer running that check would only be checking a variable.
  • The timer fires after 1 ms of quiet on the board. If any gap between the steps lasted longer, the hardware would take the link down on its own, and software would then send its own hibernate-enter to a link that's already asleep.

Once the timer is off and the link is really UP, the hardware matches the core's variable, and nothing changes the link behind software's back. The comment in the function's failure branch shows it was written for this path: “trigger error handler and break suspend”.

Step 4: what POST_CHANGE switches off

By now the chip is asleep and the link is in software hibern8, so nothing will use the host's link hardware until the next wake. Everything below is on the SoC's side; the chip took care of its own insides when it received START STOP UNIT. In order (ufs-mediatek.c:2627 to 2655):

  1. UniPro goes into power-down. UniPro is the protocol engine inside the host controller, and with the link asleep it has nothing to do. ufs_mtk_link_set_lpm() (2521) sets MediaTek's own UniPro attribute VS_UNIPROPOWERDOWNCONTROL (0xD0A8, ufs-mediatek.h:128) to 1.
  2. The M-PHY loses power. These are the host's analog transmitters and receivers. In hibern8 they were already idle, with only a small wake-up detector on; now phy_power_off() removes their power (through ufs_mtk_mphy_power_on(), 607).
  3. The SRAM is switched off. This is a block of memory built into the UFS controller. Linux can't flip its power switch directly: ufs_mtk_sram_pwr_ctrl() makes an SMC, a call into MediaTek's secure firmware, which does it. (The macro is in mainline's ufs-mediatek-sip.h; the vendor tree makes the same call.) Neither MediaTek's code nor mainline says what the SRAM holds.
  4. The clock drops, at G5 only. _ufs_mtk_clk_scale(hba, false) moves ufs_sel to the 273 MHz source and stops holding vcore at 0.65 V (2655).

A fifth action, holding the chip's reset line, runs only when the link is fully off, which doesn't happen on the board's runtime path. If any step fails, the hook marks the link as off and returns -EAGAIN, which forces a full reset instead of a normal wake later.

Waking undoes it in reverse. ufs_mtk_resume() (ufs-mediatek.c:2669) powers the SRAM back on, then the M-PHY, raises the clock if the link was at G5 (2699), then calls ufs_mtk_link_set_hpm() (2467). That function re-enables the controller (ufshcd_hba_enable()), takes UniPro out of power-down, sends DME_HIBERNATE_EXIT, and sets up the controller's request queues again. That last step is a sign the controller really lost its working state while asleep.

Added 1 Nov · The controller going to sleep, and MediaTek's wrapper

The controller sleeps right after the W-LUN (rule 3). Its sleep function is the mirror image of ufshcd_resume() above: ufshcd_suspend() turns the interrupt off, turns the clocks off (ufshcd.c:10136), and then calls ufshcd_vreg_set_lpm() (10147) for the chip's supplies:

  • chip not Active (it's in Sleep): VCC off;
  • link in hibern8 or off: VCCQ into low-power mode. The voltage stays the same, but the regulator is told the load will be at most 1 mA (UFS_VREG_LPM_LOAD_UA), so the PMIC can switch it to a low-current mode. VCCQ stays on because the chip's controller has to keep its state.

MediaTek wraps this. Its ufs_mtk_runtime_suspend() (ufs-mediatek.c:3615) calls the core's version, puts more rails into low-power mode (3626), and then switches off the power domain the whole controller sits in (MTCMOS, 3629; enabled by mediatek,ufs-rtff-mtcmos, mt6991.dts:6764). ufs_mtk_runtime_resume() (3637) does the reverse, then calls the core's wake.

So the controller's wake brings back the power domain, the supplies and the clocks. It doesn't bring back the chip's mode or the link: those belong to the W-LUN.

3.5 The sleep and wake order on the board

Going to sleep (500 ms without disk access): the LUs sleep → the W-LUN sleeps at once (chip to Sleep, link into software hibern8) → the controller sleeps (clocks off).

Waking with ufshcd_rpm_get_sync(), which names the W-LUN: rule 1 wakes the controller first (clocks on). Then the W-LUN's own wake-up runs: DME_HIBERNATE_EXIT, chip to Active, AH8 timer back on. The link is UP.

Waking with pm_runtime_get_sync(hba->dev), which names the controller: clocks on. Then, by rule 2, nothing else. The link stays in hibern8 and the chip stays in Sleep.

Update 1 Nov · Two details in this picture
  • At +500 ms the link doesn't go straight from auto-hibern8 into software hibern8. START STOP UNIT travels over the link, so the W-LUN's sleep first stops the timer and waits for the link to come back UP, then sends the command, and only then puts the link into software hibern8 (3.4).
  • “The controller sleeps (clocks off)” does more than clocks. It also switches off the chip's VCC, puts VCCQ into low-power mode and, on the board, powers off the controller's whole power domain (3.4, 3.6).

4.2 The deadlock that moved the job

The change is commit b294ff3e3449, “scsi: ufs: core: Enable power management for wlun”, by Asutosh Das and Can Guo (both at Qualcomm). It was committed on 10 May 2021 and first released in Linux 5.14. Its commit message explains what went wrong before it:

  1. When the controller went to sleep, its own sleep function sent START STOP UNIT to the chip, to put the chip to sleep first.
  2. But by rule 3, the controller only sleeps after all its children are asleep, and that includes the SCSI devices. Their request queues were already suspended.
  3. A block-layer change, 52abca64fd94 (“scsi: block: Do not accept any requests while suspended”), made any request to a suspended queue wait until the queue resumes.
  4. So the START STOP UNIT sat waiting for a queue that would never resume, and the controller's sleep waited for the command. Nothing could move. The commit message shows the stuck call chain: ufshcd_runtime_suspend → ufshcd_suspend → ufshcd_set_dev_pwr_mode → __scsi_execute → blk_get_request → blk_queue_enter → schedule.

The fix gave the W-LUN its own runtime PM and moved the chip-and-link work into its sleep and wake functions. With the device links, the W-LUN sleeps after all the LUs and wakes after the controller, so its START STOP UNIT always has a working path.

5.2 Error 1: the PMC timed out

This came from the first version, which, like Qualcomm's original (it calls ufshcd_change_power_mode() directly), sent the PMC without going through MediaTek's hooks. Whenever the board had been quiet for more than half a second, the W-LUN was asleep and the link was in software hibern8. The first line woke only the controller. The PMC was sent into a sleeping link, nothing answered, and after 500 ms the core gave up. It was first reported as “pmc command timed out”; the 6.6 core's wording is pwr ctrl cmd … completion timeout.

To be honest about this one: we never captured its full log. The sleeping link is the explanation that fits everything else, but it wasn't proven separately.

Added 1 Nov · Why it timed out, instead of failing at once
  • The PMC doesn't try to wake anything. The first line did the waking, and it reached only the controller (5.4). The PMC then went out into a link that was still asleep.
  • A PMC is a negotiation, not a wake-up. Writing PA_PWRMODE makes the host's UniPro send a power-change request across the wires and wait for the chip's confirmation (1.6). In software hibern8 the wires carry nothing until a hibernate-exit, so the request never crossed and the chip never answered.
  • The message tells you which kind of failure it was. The host accepted the command; otherwise uic error would have appeared at once (ufshcd.c:4229). What never came was the end of the exchange, so after 500 ms the result was completion timeout (4237).
  • What happened next. The core marked the link broken and scheduled the error handler (4270 to 4272). The error handler wakes the W-LUN the right way, with ufshcd_rpm_get_sync() (ufshcd.c:6381), resets the controller, and brings the link back at maximum gear. So the next disk access worked, but the requested gear was gone.

Added 1 Nov · Why stopping the timer couldn't help

MediaTek's hook assumes the link is either already UP or in auto-hibern8. In both cases, writing AHIT = 0 ends with the link UP (2.2). Software hibern8 is the case it doesn't cover:

  • AHIT was already 0, because MediaTek's suspend hook had written it before START STOP UNIT (3.4). The write didn't even change the register.
  • The hook waited 100 ms, the link never came up, and it printed exit h8 state fail and scheduled a reset (ufs-mediatek.c:2997).

The function's name says the same thing: ufs_mtk_auto_hibern8_disable() turns auto-hibern8 off. Taking the link out of software hibern8 isn't part of its job.

5.4 One bug, seen from two places

Errors 1 and 2 are the same problem. Without MediaTek's hook, the PMC itself ran into the sleeping link and timed out. With the hook, the hook noticed the sleeping link first and complained.

Added 1 Nov · The bug, row by row

This uses the ladder from 3.6. When the command was typed, the board had been quiet for more than half a second, so every rung had already happened:

The old line names the controller, and by rule 2 waking a device never wakes its children. Nothing in the controller's wake sends a hibernate-exit or tells the chip to leave Sleep. Both are the W-LUN's job, and nobody woke the W-LUN. The new line names the W-LUN. By rule 1 that wakes the controller first, and then the W-LUN's own wake undoes its rung.

5.5 Why it could look random

Within half a second of any disk access, the LUs, and so the W-LUN, were still awake, the link was UP, and the old line was enough. If the old code ever worked, that's why.

Update 1 Nov

“The link was UP” is too strong. Within half a second the W-LUN was awake, but after 1 ms of quiet the link was usually in auto-hibern8. That's still fine for the second version: MediaTek's hook stops the timer, and the controller brings the link back up by itself. For the first version, which skipped the hook, it's unclear: nothing shows whether a PMC on its own wakes an auto-hibernated link, and MediaTek's code doesn't rely on it.

Added 1 Nov · Why normal disk use never hit this bug

Normal reads and writes come in from the bottom of the tree, and runtime PM wakes everything they depend on:

  1. A read on /dev/sda goes to that LU's queue, and the block layer wakes the LU before sending the command.
  2. The LU depends on the W-LUN through a device link with DL_FLAG_PM_RUNTIME (ufshcd.c:5093), so the W-LUN wakes first: hibernate-exit, chip to Active.
  3. Before that, the W-LUN's parents bring the controller up.

So every read wakes the controller, the chip and the link before its command goes out. The debugfs path came in from the top, at the controller, and waking a device never wakes anything below it.

5.6 The #if 0 manual hibern8 exit

The ported code has a disabled block that called ufshcd_uic_hibern8_exit() directly. It aimed at the right symptom, but it would only have woken the link. The chip would still be in Sleep from START STOP UNIT, and the core's records would still say the W-LUN is suspended and the link is in hibern8, because ufshcd_uic_hibern8_exit() doesn't update hba->uic_link_state; its callers do (ufshcd.c:4413). The next real wake-up would then most likely send DME_HIBERNATE_EXIT to a link that's already awake, and fail. Waking the W-LUN does all three things, in the order the core expects.

Qualcomm's original also enters and exits hibern8 by hand, but for a different reason: around its clock switch, so that auto-hibern8 can't race it (ufs-debugfs.c:1237 in msm-4.19).

What happens now when you write power_mode after half a second of quiet:

  1. The controller wakes: power supplies, clocks, interrupt.
  2. The W-LUN wakes: DME_HIBERNATE_EXIT (link UP), START STOP UNIT (chip Active), AHIT timer back on.
  3. MediaTek's PRE_CHANGE sets AHIT to 0; the link is already UP, so the check passes.
  4. The PMC runs over an awake link. POST_CHANGE puts AHIT back.
  5. The code releases everything, and half a second later the whole chip side sleeps again.
Key point

MediaTek's own clkscale_control path never had this bug: it calls ufshcd_rpm_get_sync() before anything else (ufs-mediatek.c:2322 and 2398). The fix makes the path follow the same recipe.

Added 1 Nov · The rule the fix follows, and who else follows it

The debugfs code never calls MediaTek's hook itself; ufshcd_config_pwr_mode() does. So the requirement falls on whoever calls ufshcd_config_pwr_mode(), and it comes down to two lines:

  1. ufshcd_rpm_get_sync() holds the W-LUN awake. If the W-LUN is asleep, this wakes it, which takes the link out of software hibern8. If it's awake, this only stops it from sleeping until the hold is released. Either way, the link can't be in software hibern8 while the hold lasts.
  2. ufshcd_hold() keeps the clocks on. It also covers the one other way into software hibern8, clock gating. That never happens on the board (2.2), and on boards where it does, ungating exits hibern8 before ufshcd_hold() returns (ufshcd_ungate_work(), ufshcd.c:1751).

Every caller in the kernel follows this: MediaTek's clkscale_control path (ufs-mediatek.c:2322), the error handler (ufshcd.c:6381), and probe and reset, which run their PMC right after link startup, on a link that has never slept. The old debugfs function was the only caller that skipped it.

Nothing enforces it. ufshcd_config_pwr_mode() doesn't check whether the W-LUN is awake; the rule lives only in how the callers are written. That's why the old code compiled and ran, and only failed in the hardware.

And echo 4 is not part of the fix (6.4).

6.2 The other changes in file 06

Changed 1: the mode digits

The ported code had a “failsafe” block that forced FAST mode, using a variable called pwr. There is no pwr in the ported function, so it wouldn't compile, and forcing FAST would turn every SLOW (PWM) request into a FAST one. (The block looks like it came from an early version of file 05, which had both problems.) File 06 replaces it with:

        if (desired_pwr_mode->pwr_rx == FASTAUTO_MODE)
                desired_pwr_mode->pwr_rx = FAST_MODE;
        else if (desired_pwr_mode->pwr_rx == SLOWAUTO_MODE)
                desired_pwr_mode->pwr_rx = SLOW_MODE;
        desired_pwr_mode->pwr_tx = desired_pwr_mode->pwr_rx;

Why map the AUTO modes at all? MediaTek's ufs_mtk_pre_pwr_change() (ufs-mediatek.c:1908) asks a shared core helper, ufshcd_get_pwr_dev_param(), to agree the final settings. That helper only treats FAST_MODE as high speed:

MediaTek only prints failed to determine capabilities and carries on, so the PMC would go out asking for gear 0 on 0 lanes. SLOW requests are fine, because MediaTek switches the helper into PWM mode for them.

The same helper also gives TX and RX the same gear (the lower of the two requested) and the same mode, caps lanes at 2, and sets rate B. So 342211 becomes G3 in both directions.

Added 1 Nov · Is the whole function OK? A review

Yes: the part that matters is right. The question came up once the fio speeds started following the gear. It isn't luck:

  • The ported function does the same steps, in the same order, as the core does before its own gear changes (ufshcd_clock_scaling_prepare()): wake, keep the clocks on, take clk_scaling_lock, block new commands, wait for the ones in flight, then the PMC.
  • The wake is the core's own helper, the one its debugfs files already use (ufs_debugfs_get_user_access(), ufs-debugfs.c:68).
  • The PMC goes through ufshcd_config_pwr_mode(), so MediaTek's hooks run. Those hooks send only link commands (DME), nothing that needs clk_scaling_lock, so holding that lock can't deadlock against them.

Three things still worth changing:

  1. Delete the ported clock block. The reasons are in the 6.3 update below.
  2. Move the debug dumps. The body of ufshcd_dump_uic_state() wasn't available. If it reads controller registers, two of its calls can run while the clocks are off: the “before hold” one, and the one in the access-failure path. MediaTek turns the clocks off 10 ms after the last command (ufs-mediatek.c:1471), but the W-LUN stays awake for about 500 ms. In that gap the wake does nothing and the clocks are off, and a register read there can hang the bus. Move the first call below ufshcd_hold(). Delete the failure-path one, which only runs during shutdown.
  3. Take the lock once per boot (echo 5, then echo 4; see the 6.4 update).
Watch out

Any UFS error resets the link to maximum gear and lanes without telling you. After each fio run, check dmesg | grep "err_handler started". If that line appears, the run wasn't at the requested gear.

6.3 The ported clock-scaling lines

What they try to do: slow the controller's clock when the link goes down to G1, and speed it up for anything higher, by calling ufshcd_scale_clks() before or after the PMC.

What actually runs on MT6991:

  1. ufshcd_scale_clks() first calls MediaTek's clk_scale_notify hook, which returns at once (ufs-mediatek.c:3172). The core's clock scaling is switched off on this board: the device-tree flag mediatek,ufs-clkscale-only-by-user (mt6991.dts:6768) makes MediaTek skip setting UFSHCD_CAP_CLK_SCALING (ufs-mediatek.c:1763).
  2. Then the core's ufshcd_set_clk_freq() walks its list of clocks. ufs_sel is still on that list, with 273 and 499.2 MHz from the device tree; MediaTek removes only the two source clocks from the list (ufs-mediatek.c:1240). So the core calls clk_set_rate(ufs_sel, …), unless it believes the clock is already at that rate.
  3. MediaTek's own path makes the same switch differently (_ufs_mtk_clk_scale(), ufs-mediatek.c:3039). It raises vcore to at least 0.65 V before moving ufs_sel to the fast source with clk_set_parent(), and lowers vcore only after moving to the slow source. The core's path never touches vcore.

Is that safe? Slowing a clock down is always safe. Speeding it up to 499.2 MHz is safe only if vcore is already high enough. After echo 4 > clkscale_control, MediaTek has raised vcore, and the lock stops anyone lowering it, so it's fine. The risky combination is echo 1 or echo 3 (MediaTek drops vcore to its minimum) followed by a G5 request through power_mode.

Two things not checked. Whether clk_set_rate() really moves this mux depends on MediaTek's clock driver, which wasn't read. And ufshcd_scale_clks() is static in the stock android15-6.6 ufshcd.c (line 1128); since the build links, the board's tree must make it visible, probably as part of the port.

Correction

An earlier explanation said these lines were harmless because MediaTek's clock-scale hook does nothing. The hook does nothing, but the core still calls clk_set_rate() on ufs_sel. The conclusion stands (safe after echo 4; don't mix with 1 or 3), but the reason given was incomplete.

Update 1 Nov · The clock block, looked at again

Two things missed earlier, and a recommendation.

MediaTek also moves the clock by itself, at G5

On the board MediaTek's suspend hook drops ufs_sel to 273 MHz whenever the link goes to sleep at G5, and its resume hook raises it again (ufs-mediatek.c:2655, 2699). The ported function wakes the W-LUN first, so at G5 the clock is always back at 499.2 MHz before the PMC runs.

Where the risk really is

If nothing writes clkscale_control, the path stays consistent. We traced G5 → G1 → G5 → G4 with the W-LUN asleep before each write, and the clock is at 499.2 MHz whenever the gear is above G1. The risk needs a MediaTek scale-down (1 or 3) first. That moves ufs_sel to 273 MHz with clk_set_parent() and stops holding vcore at 0.65 V, without updating the core's record of the clock, clki->curr_freq. A G5 request through power_mode afterwards then goes one of two ways:

  • If curr_freq still says 499.2 MHz, ufshcd_scale_clks(hba, true) sees nothing to do. The link runs G5 on the 273 MHz clock until the next sleep and wake.
  • If curr_freq says 273 MHz (after a G1 visit), the core raises the clock with clk_set_rate() but never touches vcore. That's the case the text above warns about.

What either state actually does can't be told from the code: maybe it's only slower, maybe it causes link errors. MediaTek's own code never produces either.

Recommendation: delete the block

  • It does almost nothing on the board. ufs_sel is the only clock in the table. For G2 to G5 the block either does nothing or undoes its own earlier G1 change.
  • Its one real action is a call MediaTek avoids. For G1 it calls clk_set_rate(ufs_sel, 273 MHz). MediaTek's comment above ufs_mtk_clk_scale() (ufs-mediatek.c:3140) explains their design: they switch the clock's source themselves first, so that the core's clk_set_rate() finds the rate already set and does nothing. The reason they give is to avoid “changing rate of pll clock that is shared between modules”. The port's G1 path is the one place where the clock framework picks the source by itself. It probably picks the 273 MHz one, and nothing seen so far suggests otherwise, but MediaTek's flow never exercises it.
  • Deleting it costs nothing. The clock rule only works one way (1.3): G1 with the clock at 499.2 MHz is the normal state during every boot.
  • If you'd rather keep it, check once: run grep -iE "ufs|mainpll|univpll" /sys/kernel/debug/clk/clk_summary before and after a G1 write. No PLL rate should change, and ufs_sel's source should be mainpll_d4_d2.
Plain words

“Don't gear changes need clock scaling?” Only if something can lower the clock. On the board three things can: this block itself (at G1), clkscale_control 1 or 3, and MediaTek's own sleep at G5, which its wake undoes. Delete the block and take the lock, and the clock never goes down, so it never needs to come back up. The block creates the very need it then fills.

6.4 clkscale_control, and why echo 4 first

MediaTek's sysfs file takes six values. This is its own help text (ufs-mediatek-sysfs.c:688), with what each value does on the board:

ValueHelp textOn the board
0free runRefused: needs the core's clock scaling, which is off (“only by user”)
1scale downG4 and the 273 MHz clock (min_gear = UFS_HS_G4), vcore lowered
2scale upMax gear and 499.2 MHz. The value at boot.
3scale down and forbid changeLike 1, then locked
4scale up and forbid changeLike 2, then locked
5allow change and free runRemoves the lock

What echo 4 does, through clkscale_control_store() (ufs-mediatek-sysfs.c:710), ufs_mtk_dynamic_clock_scaling() (ufs-mediatek.c:2364) and ufs_mtk_config_pwr_mode() (ufs-mediatek.c:2271):

  1. Wake the W-LUN (ufshcd_rpm_get_sync()), block new commands, hold the clocks, wait for the doorbell to clear.
  2. Raise vcore, ask the CPUs for low wake-up latency (a PM QoS request), move ufs_sel to 499.2 MHz.
  3. PMC to max_gear, then print PMC Success! [RX, TX]: gear=….
  4. Release everything, then set clk_scale_forbid = true.

Why it helps while you experiment:

  • The clock and vcore are ready for G5.
  • With the forbid flag set, every later call to ufs_mtk_dynamic_clock_scaling() returns at its first line. Its callers are writes to clkscale_control and the eye-monitor scan (eyemon_scan()). The store function accepts a powerhal_set: prefix, which means Android's PowerHAL writes this file at runtime. Without the lock, one of those writes could run its own PMC and replace the setting.
Watch out

echo 2 or echo 4 will not take you back to max gear after you've changed the gear through power_mode. ufs_mtk_dynamic_clock_scaling() remembers its last request in a static variable, scale_mode. If that was already “scale up”, it returns without a PMC; it doesn't know power_mode moved the gear. Write the max mode through power_mode, or reboot. echo 5 removes the lock.

Update 1 Nov · echo 4 is a lock, not part of the fix

Does the fix work without echo 4? It does. What fixed exit h8 state fail is the W-LUN wake at the top of the ported function, and echo 4 can't be doing that job: MediaTek's handler wakes the W-LUN only for its own PMC and lets go at the end. With a 0 ms delay, the W-LUN is asleep again long before the next command. Test 3 (8.5) checks this on the board.

What the lock buys you

  • The requested gear can't be overwritten. Any write of 1 to 4 runs MediaTek's own PMC: 1 and 3 set G4, 2 and 4 set the maximum gear. It copies hba->pwr_info (ufs-mediatek.c:2280), so it keeps the current lanes and mode and changes only the gear. With the lock set, every later write returns at the first check in ufs_mtk_dynamic_clock_scaling() (2376).
  • Two PMCs can't interleave. MediaTek's path takes neither host_sem nor clk_scaling_lock, so a clkscale_control write while a power_mode write is running could mix its PMC steps with the other's.
  • No G5 on the slow clock. The risky combination in the 6.3 update needs a 1 or 3, and the lock blocks both.
Try it: once per boot, before the writes 
C=/sys/bus/platform/devices/16810000.ufshci/clkscale/clkscale_control
echo 5 > $C
echo 4 > $C

The 5 comes first in case something already wrote 3 (scale down and lock). In that case a bare 4 hits the lock check and does nothing. On the board 5 never runs a PMC; it only clears the lock.

  • A free detector. The current: line still changes when someone writes the file, even when the lock makes the write do nothing, because the store function records the value either way. If it later shows anything other than 4, something else on the system is writing this file.
  • About PowerHAL. The text above says PowerHAL writes this file. That's an inference from the powerhal_set: prefix; it hasn't been confirmed on the build. The detector will tell.

What “only by user” means

The device-tree flag mediatek,ufs-clkscale-only-by-user (mt6991.dts:6768) means clock scaling happens only when user space asks for it, by writing clkscale_control. “User” is the kernel's word for anything outside the kernel, PowerHAL included, not necessarily a person.

  • MediaTek reads the flag into its own capability bit (ufs-mediatek.c:826). With that bit set, MediaTek doesn't turn on the core's clock scaling (1763), so the core never calls ufshcd_devfreq_init() (ufshcd.c:8763). There is no governor watching how busy the disk is.
  • That's also why clkscale_control exists on the board: the clkscale/ directory is created only if the core's scaling or this flag is on (ufs-mediatek-sysfs.c:1061). And it's why 0 (“free run”, hand control back to the governor) is refused (ufs-mediatek-sysfs.c:736): there is no governor to hand it to.
  • MediaTek never sets G2 or G3 itself, and its only lower gear is G4. G1 appears only at boot (as PWM-G1) and in its debug code (1.3).
Watch out

Don't write to upthreshold or downdifferential, the two files next to clkscale_control. They tune the governor that doesn't exist here, and both store functions call mutex_lock(&hba->devfreq->lock) without checking for NULL. hba->devfreq is NULL on the board, so writing a number to either file causes a kernel oops. Reading them is safe.

7How we got here, and where we went wrong

7.1 The path, in order

  1. The question. The starting point: the board, clkscale_control, the ported debugfs code and the two errors, and a search for a ready-made fix.
  2. The search. We went through upstream Linux, MediaTek's vendor trees and the patch archives. No patch fixes this exact failure. Two are related, and neither fixes it: 7dec5cedf7b2 (“scsi: ufs: core: Serialize AHIT register access between sysfs and host driver”) and f29ec85ac4fd (“scsi: ufs: host: mediatek: Return error directly on idle wait timeout”). We downloaded MediaTek's MT6991 vendor code (OnePlus's public copy), the android15-6.6 core files and Qualcomm's msm-4.19 ufs-debugfs.c, so the three could be read side by side.
  3. One step at a time. The first explanation was too compressed, so we slowed down and went through it a question at a time. What does disabling AH8 actually do? Must the link be up before a PMC? Why would the W-LUN's suspend have sent DME_HIBERNATE_ENTER? Why is there a separate step that powers UniPro down?
  4. Code to compare. Files 01 to 05 were written into this folder, to open side by side in an editor.
  5. The flow. The ported code's sequence: pm_runtime_get_sync(), hold, lock, block, doorbell, PMC, plus the ported clock lines. Its first step was the root cause: it woke hba->dev, not the W-LUN.
  6. The clock question. Keep the ported clock-scaling lines, or copy MediaTek's? We settled on keeping them, setting clkscale_control to 4 first, and never mixing with 1 or 3.
  7. The ported code. The code switched to ufs_debugfs_get_user_access() (from file 05) on 31 October. It was copied into file 06, with two more fixes marked.
  8. The test. We rebuilt the kernel image, set clkscale_control to 4 and wrote power_mode: no exit h8 state fail. Then the lane tests passed too.

8.1 Results so far

  • With the fix, and clkscale_control at 4: no exit h8 state fail.
  • Lane changes from 2 to 1 pass.

Two more checks turn that into proof. If you've already run them, skip ahead.

Added 1 Nov · Reported since
  • The fio speeds follow the gear that was set. That's the physical check from 8.3, done with fio instead of dd.

8.2 Test 1: recreate the old failure condition

The old failure needed the W-LUN asleep. But echo 4 wakes the W-LUN for a moment (its first scale-up after boot does), so a write right after it could pass even with the old code. Make sure the W-LUN is asleep before you write:

Try it 
W=/sys/bus/scsi/devices/0:0:0:49488/power/runtime_status   # the UFS Device W-LUN
cat $W                  # repeat until it says: suspended
cat $W; echo 112211 > /sys/kernel/debug/…/power_mode; dmesg | tail

It passes if you see suspended, then no exit h8 state fail, and state=1. If 0:0:0:49488 isn't there, find it with ls /sys/bus/scsi/devices | grep 49488.

8.3 Test 2: did the gear really change?

“No error” isn't proof, for four reasons:

  1. The write never fails in the shell. ufsdbg_power_mode_write() ends with return cnt; even when the PMC failed, so echo always looks successful. Only dmesg tells you.
  2. The success line in dmesg isn't from power_mode. PMC Success! [RX, TX]: gear=… comes from MediaTek's ufs_mtk_config_pwr_mode(), that is, from echo 4. The core path prints nothing on success (ufshcd_print_pwr_info() uses dev_dbg, ufshcd.c:697).
  3. Asking for the current mode does nothing. If the request equals the current settings, ufshcd_change_power_mode() returns 0 without sending a PMC (“power already configured”, ufshcd.c:4566). Right after echo 4 the link is at max gear, so asking for max gear tests nothing.
  4. cat power_mode shows what the core believes. It prints hba->pwr_info, which the core updates only after a successful PMC (ufshcd.c:4638). That's good evidence, but it's still software reporting on itself.

The physical check: the wire sets a speed limit. Whatever the software says, data can't move faster than the lanes carry it. The ceiling is bits per second × 0.8 (for 8b/10b) × number of lanes ÷ 8 bits per byte:

GearBits/s per laneData per laneCeiling, 2 lanes
HS-G1B1,457.6 M146 MB/s~290 MB/s
HS-G3B5,830.4 M583 MB/s~1.17 GB/s
HS-G4B11,660.8 M1,166 MB/s~2.3 GB/s
HS-G5B23,321.6 M~2,870 MB/s (128b/130b)~5.7 GB/s

These are ceilings before protocol overhead; real numbers land below them.

Try it

Go to G1 (112211), then:

echo 3 > /proc/sys/vm/drop_caches     # every run, or the read comes from RAM
dd if=/dev/block/sda of=/dev/null bs=1M count=1024

At G1, anything above about 290 MB/s means the link isn't at G1, because that's physically impossible. Then run the same at max gear and compare. Use G1 rather than G3: a simple dd may not fill a G3 link, so G3 and max gear could show similar numbers, while G1 is an unmistakable drop.

8.4 Reading the state= print

state=1 (OPERATIONAL) means all good. state=3 (EH_SCHEDULED_FATAL) means MediaTek's link check failed and a reset is queued: the old failure is back, so look at what woke (or didn't wake) the W-LUN.

10Glossary

AH8 (auto-hibern8)
The controller puts the link into hibern8 by itself after an idle time, and wakes it by itself when new commands arrive.
AHIT
The controller register (offset 0x18) that holds the AH8 idle time. 0 means off.
clk_scale_forbid
MediaTek flag set by clkscale_control values 3 and 4. It blocks MediaTek's own clock and gear changes until value 5 clears it.
Clock gating
Switching the controller's clocks off during short idle gaps (at least 10 ms on MediaTek). Separate from runtime PM. ufshcd_hold() blocks it.
DME
The part of UniPro that takes management commands from the driver: DME_GET, DME_SET, DME_HIBERNATE_ENTER, DME_HIBERNATE_EXIT.
Doorbell
Controller register (offset 0x58) with one bit per command slot. The driver sets a bit to start a command; the controller clears it when the command is done.
EH (error handler)
The core's recovery work. It resets the controller and restarts the link.
Gear
Bits per second per lane. HS-G1 to G5 are the fast family; the PWM gears are the slow one.
GKI
Google's Generic Kernel Image, the common kernel that holds the UFS core.
hba
“Host bus adapter”: the core's struct ufs_hba, describing one controller. hba->dev is the controller's struct device.
Hibern8
The link's deepest sleep that keeps its settings.
host_sem
The core's semaphore that keeps user requests, error handling, system suspend and shutdown from overlapping.
Lane
One pair of wires carrying data in one direction.
LU
Logical unit: a readable, writable slice of the chip (sda, sdb, …).
M-PHY
The electrical layer: the wires, their voltages, and recovering bits and timing from them.
PMC
Power mode change: switching gear, lanes or mode.
Rate A, rate B
The two base frequencies for HS gears. MediaTek uses B.
Runtime PM
Linux's per-device sleep and wake while the system is running.
SSU (START STOP UNIT)
The SCSI command that sets the chip's power mode: Active, Sleep, PowerDown.
UIC command
A command for the link layer, written to controller register 0x90.
UniPro
The link layer: frames, acknowledgements, re-sending, speed and power state.
UPIU
The packet format that carries SCSI commands over UFS.
vcore
The SoC's core supply voltage. The 499.2 MHz ufs_sel source needs at least 0.65 V.
vops
The table of vendor hooks that the core calls.
W-LUN
Well-known logical unit. The UFS Device W-LUN (0xD0, shown by Linux as 0:0:0:49488) stands for the whole chip.
Added 1 Nov · More terms
Device link
A “depends on” arrow between two Linux devices. Each LU depends on the W-LUN, so waking an LU wakes the W-LUN first.
devfreq
Linux's framework for changing a device's frequency according to load. The core's UFS clock scaling uses it. It's never started on the board (“only by user”).
MTCMOS
MediaTek's name for a switchable power domain inside the SoC. On the board MediaTek switches off the UFS controller's domain after the controller sleeps.
PACP
The control frames that UniPro's lowest layer sends over the link. A PMC is a PACP_PWR_req from the host and a PACP_PWR_cnf back from the chip.
PMIC
Power-management chip: the separate chip (MT6363 here) whose regulators make the board's supply rails, including the UFS chip's VCC and VCCQ.
Power level (rpm_lvl)
The core's pairing of a chip power mode with a link state, from ufs_pm_lvl_states[]. The board's runtime level, 3, is {Sleep, hibern8}.
Reference clock
The steady clock the host supplies to the chip's side of the link. MediaTek stops it once the link is in hibern8.
setup_clocks
The vendor hook the core calls whenever it turns the controller's clocks on or off: in clock gating, and in the controller's own sleep and wake.
SMC
Secure monitor call: an instruction that asks the secure firmware to do something Linux isn't allowed to do directly. MediaTek uses one to power the UFS SRAM on and off.
SRAM
On-chip memory. The UFS controller has a block of it, which MediaTek switches off when the chip side sleeps. The code doesn't say what it holds.
Symbol clock
A clock running at the link's own rate: unipro_tx_sym for sending, and one receive clock per lane (unipro_rx_sym0, unipro_rx_sym1), recovered from the arriving bits.
uic_link_state
The core's record of the link's state. Only software moves update it; auto-hibern8 doesn't.
UniPro power-down
MediaTek's own UniPro attribute, VS_UNIPROPOWERDOWNCONTROL (0xD0A8). It's set to 1 when the chip side sleeps, so the host's UniPro engine stops.
VCC
The supply rail for the chip's flash memory. The host switches it off once the chip is in Sleep.
VCCQ
The 1.2 V supply rail for the chip's controller and its end of the link. On the board's runtime sleep it goes into low-power mode, never off.
